# DLSAuto — правила для Claude Code

Перед любой задачей прочитай `docs/DEV_CONTEXT.md` — это источник правды по разработке. Продукт и дизайн — `docs/PROJECT_CONTEXT.md`, правила визуала — `docs/DESIGN_RULES.md`. Промпт текущего этапа — в `docs/stages/`.

## Всегда

- Язык: UI — украинский (ru — второй язык через `/ru`), код и коммиты — английский, общение — русский.
- Дизайн-система раньше страниц: токены → примитивы → составные → `/ui` → страницы. Новый стиль на странице — не писать, вернуться в компоненты.
- Унификация, не редизайн: значения (размер, отступ, радиус, цвет) можно свести к канону; структуру, состав, порядок, раскладку, тексты — не менять. Сомневаешься — спроси.
- Ничего не выдумывать: категории, модели, цифры, названия — только из `docs/`; остальное — плейсхолдер с пометкой.
- Расширение модели данных сверх `DEV_CONTEXT.md §4` — только с согласованием и сразу с правкой §4 в том же коммите.
- Server Components по умолчанию; анимации — только transform/opacity + `prefers-reduced-motion`.
- Внешние сервисы — только через `src/integrations/<name>`; все операции синхронизации идемпотентны; недоступность KeyCRM не ломает заказ.
- Секреты — только в env; `.env.example` актуален.

## Процесс

- Работа ведётся прямо в `stage`. `main` — релизная ветка, обновляется только мержем из `stage` по команде владельца. Фича-веток нет.
- Conventional Commits. TypeScript strict, без `any` без комментария.
- Новая зависимость — строка в README с причиной.
- В конце задачи — отчёт: сделано / не сделано и почему / что проверить руками.
- В конце этапа: отчёт в `docs/stages/`, обновить `docs/ROADMAP.md`; новое архитектурное решение — ADR в `docs/decisions/`.
- Задача противоречит `docs/` — спросить, прежде чем нарушать.

## Известные грабли — не повторять

Каждый пункт — реальная ошибка из этого проекта. Поймали новую — добавь строку сюда в том же коммите, что и исправление.

- Сервисы (Postgres, Redis и т. п.) — только через docker compose. Никаких нативных установок в devcontainer, даже «временно для проверки». Если Docker недоступен — остановись и скажи, не обходи.
- Инструменты в devcontainer (git-lfs, gh, corepack) — только через features в devcontainer.json. Поставленное руками исчезает при пересборке.
- Цвета и типографику не «сводить к ближайшей ступени» — шкалы есть только у размеров, отступов, радиусов, высот контролов. Цвет — точное значение из экспорта, близкие оттенки — разные токены.
- Чистый #FFFFFF не удалять, если он есть в экспорте.
- Поля модели данных — строго по DEV_CONTEXT §4. Нужно новое поле — спроси; добавил — правь §4 в том же коммите.
- Редакционные тексты (подписи, описания, условия) — в Payload, не в коде. В коде — только UI-строки словаря i18n.
- Не выдумывать данные: категории, модели, цифры, названия деталей — только из docs/. Нет данных — плейсхолдер с пометкой и запись в открытые вопросы.
- Зависимости — только с согласования, со строкой-обоснованием в README.
- Запиненные версии (pnpm, Next, Payload, Node) не обновлять по подсказкам из консоли. Обновление версий — отдельная задача по команде.
- Ветки: работа в stage, фича-веток нет. main — только мерж из stage по команде владельца.
- Хуки (husky, lint-staged) не обходить через --no-verify без явного разрешения.
- husky + Git LFS: при husky `core.hooksPath=.husky/_` штатные LFS-хуки в `.git/hooks` не выполняются, и `git push` падает с `GH008 (unknown Git LFS objects)` — LFS-объекты не загружаются. LFS-хуки (`pre-push`, `post-checkout`, `post-commit`, `post-merge` → `git lfs <hook> "$@"`) должны лежать в `.husky/`, рядом с `pre-commit`/`commit-msg`.
- Падающие проверки не «чинить» ослаблением: eslint-disable, test.skip, расширение allow-листов, смягчение CI — только с согласования.
- Структуру дизайна не менять: состав, порядок, раскладку, тексты. Унификация — только значения, в пределах 2px.
- Разметка: никаких псевдоэлементов для декора, absolute для раскладки, системных шрифтовых стеков вместо макетного шрифта, текста, разбитого на span.
- Миграции Payload запускаются из worker-образа одноразовым сервисом migrate; в standalone web-образе CLI нет.
- `payload migrate` (стоковый CLI) зависает намертво в любом не-TTY (CI, devcontainer, пайп, `< /dev/null`), если в БД есть dev-push-маркер — строка `name='dev', batch=-1` в `payload_migrations`, которую пишет `next dev` при динамическом пуше схемы. В этом случае `@payloadcms/drizzle/dist/migrate.js` показывает интерактивный `prompts`-запрос «you've run in dev mode… data loss will occur. proceed? (y/N)», а ветка `migrate` в CLI не прокидывает `--force-accept-warning` в `adapter.migrate()` — заглушить флагом нельзя. На чистой БД (CI/Docker/prod, `NODE_ENV=production` → пуша нет → маркера нет) всё работает, поэтому «локально висит ≠ в Docker висит». Фикс: `pnpm db:migrate` зовёт `src/payload/migrate.ts` — он чистит маркер `batch=-1` (эквивалент ответа «yes») и гонит цепочку неинтерактивно; лежит в `src/` (не `scripts/`), т.к. worker-образ копирует `src`, но не `scripts`. Ручное применение SQL через psql больше не нужно.
- .env и секреты не коммитить; .claude/settings.local.json и AGENTS.md — в .gitignore, .claude/settings.json — в репо.
- Утверждённые страницы («Контакти», хедер, футер и далее по этапам) не менять без задачи; любая правка в них — со сверкой скриншотами до/после.
- Не делать молча работу «сверх задачи» (рефакторинг соседнего кода, переименования) — это отдельный вопрос.
- Заблокированная команда (сеть, пуш, sudo) — не обход, а сообщение владельцу с готовой командой.
- rAF/скролл-эффекты: в cleanup сбрасывать id-реф в `undefined`, а не только `cancelAnimationFrame`. StrictMode в dev монтирует эффект дважды; оставшийся «правдивый» (отменённый) id блокирует guard `if (raf.current) return` навсегда — скролл-скраб мёртв только в dev. Поймано на «Шлях деталі».
- `pnpm devsafe` удаляет `.next` вместе с прод-сборкой. Перед `pnpm start` / Lighthouse — свежий `pnpm build`.
- `not-found.tsx` не умеет экспортировать metadata (Next владеет `<title>`; хойстед `<title>` игнорируется, а `<meta robots>` проходит). Локаль — из request-заголовка в middleware; заголовок вкладки — через `title.default` лейаута.
- Lighthouse гонять по прод-сборке (`pnpm start`), не по dev; страница с не-200 статусом (реальный 404) получает 0 — это статус, не качество.
- После `pnpm db:seed` dev-страница не отражает новые данные, пока не очищен весь `.next`: `getPage` обёрнут в `unstable_cache` (revalidate не задан, тег `pages` сид извне не ревалидирует), плюс персистентный кэш Turbopack в `.next` держит старый RSC-рендер. Рестарт dev и чистка только `.next/cache` не помогают. `rm -rf .next` заблокирован хуком — чистить `find .next -mindepth 1 -delete`, затем рестарт. Прод-фикс (отдельная задача): afterChange/afterDelete-хуки коллекций → `revalidateTag`, иначе правки в админке тоже не видно.
- Бизнес-правила — из DEV_CONTEXT (§4–6), визуал — из экспорта. Совпадение в демо-данных экспорта (напр. бегущая рамка нарисована там же, где скидка) — не правило: рамка привязана к `featured`, «−N%» и перечёркнутая цена — к `discountPercent` (разные слоты карточки). Экспорт показывает как выглядит, DEV_CONTEXT — когда показывать.
- Снятое из плана этапа — не делать без команды владельца. Если ранее договорились отложить/убрать фичу, не возвращать её по своей инициативе. (05.11: car-fit был в «Рамках/отложено» на этапе ProductCard, вернули только по команде владельца; сезонные наклейки остались отложенными до этапа 11.)
- Иконки масштабируются только ступенями `--icon-16/20/24/32/40`. `var(--icon-14)` (или любой нешкальный шаг) не определён — SVG без width/height растягивается на весь контейнер (в quick-view бейдж-иконки 14px вылезли на пол-модалки). Экспортные 14px-иконки — явным rem (`0.875rem`), не `var(--icon-14)`.
- Коллекция с доступом `publishedOrStaff` обязана иметь `publishedField` в `fields` — иначе любой гостевой запрос падает с 400 «cannot be queried: published». `brands` ссылалась на `published` в docstring, `defaultColumns`, доступе и сиде, но поля не было — `getBrands` падал при первом же использовании (heroB). Добавляешь коллекцию с `publishedOrStaff` — сразу клади `publishedField`.
- Визуал и состав страницы — по экспорту Claude Design, не по PROJECT_CONTEXT. Блок описан в документах, но его нет на канвасе — не строить, спросить. Ничего не добавлять и не убирать: иконки, кнопки, индикаторы, анимации, фото — ровно как в экспорте. Шрифты и цвета — замер из экспорта, не из шкалы. Перед блоком — манифест из экспорта, после — сверка по счёту элементов и pixel-diff. (Поймано на «Про компанію»: выдуманные блоки/иконки/видео, свёрстано «по смыслу» вместо экспорта.)
- Сверка «расхождений нет» засчитывается **только** парой скриншотов «экспорт / реальная вёрстка» одного участка на одной ширине, снятых в браузере с данными сида (`.dc.html` экспорта рендерится статик-сервером `docs/design-export` + `support.js`; вёрстка — реальная страница). Сверка «по коду» или «по DOM» не считается и уже раз пропустила грубые расхождения страницы товара (правая колонка «Доставка»/«Приймаємо» без белых карточек и плашек, нечитаемый Delivery, обрезанный Apple Pay, пустой чип марки, артикул выдан за OEM), которые в отчётах значились пройденными. Пары — в `docs/stages/stage3c/compare/`. Харнесс: Playwright (`@playwright/test` → `chromium`; резолвить из `/workspaces/dlsauto/node_modules` через `createRequire`). Интерактив (мега-меню, sticky-bar, quick-view) в headless dev не открывается программно (code-split + StrictMode/HMR глушат скролл/клик-эффекты) — проверять форсированно (выставить `data-in`/state через `page.evaluate`) или на прод-сборке, не считать «сломанным» по невидимости в dev.
- При проверке внешней документации обходить все разделы, а не один. Вывод «фичи нет» делать, только просмотрев смежные разделы. (Поймано в ревью каталога: заключили «у KeyCRM нет вебхука остатков» по разделу вебхуков-автоматизации заказов/лидов, а он в разделе «Товари та склад» — `transferring-balance-changes-via-webhook`.)
- Сетку (ширину контейнера, боковые отступы секций) проверять на 390 / 1280 / 1536 / 1920, не только на 1280. Расхождение контейнеров 1312↔1376 было невидимо на 1280/390 (контейнер упирался в ширину вьюпорта) и проявлялось только на широких экранах ≥1376. Ширину страницы задаёт только `<Container>`; `--container-max` вне `src/components/ui/layout.tsx` запрещён (`pnpm check:container`).
- Сборка (`pnpm build`, CI-шаг `Build` и Docker-таргет `builder`) идёт **без доступа к БД** — Postgres в CI/Docker нет (Dockerfile: «no DB access needed»). Поэтому ни одна страница не должна пре-рендериться с запросом к Payload/Postgres на этапе сборки: фронтовый лейаут `src/app/(frontend)/[locale]/layout.tsx` — `force-dynamic`, данные кешируются через `unstable_cache` + ревалидация тегами. Локально сборка была «зелёной» только потому, что у владельца поднят Postgres (docker compose) и преконнект проходил. (Поймано 26.11: CI/Deploy красные с 04.11, когда home начал читать `getPage`; отчёты 3b/3c писали «зелёно» по локальному прогону.)
- `pnpm install --prod` (Docker-таргет `prod-deps` для worker-образа) пропускает devDependencies, включая husky, но всё равно запускает корневой скрипт `prepare` → `husky: not found` → установка падает. `prepare` сам пропускает husky в CI/production/`HUSKY=0` (гард в package.json); Docker-стейджи ставят `ENV HUSKY=0`. Git-хуки — локальная забота дева, в образ `.husky` не кладётся (`.dockerignore`).
- В начале сессии — смотреть статус последнего прогона Actions (оба workflow). «Зелёное» в отчёте — только после реального прогона шагов CI в **чистом клоне** (`pnpm quality` + `docker build --target web` и `--target worker`), а не локальной рабочей копии: локально есть Postgres и установленный husky, которых в CI/Docker нет, поэтому «локально зелёное» ≠ «CI зелёное». Один источник правды для quality-шагов — `pnpm quality` (его же зовёт CI).
- Доступность (DEV_CONTEXT §5, Р39) фильтруется в запросах только по полю `status` — грабли. `reserved` и «проданный по количеству» держат в БД `status = in_stock` (меняются только `quantity`/`inReserve`), поэтому `where: { status: { equals: 'in_stock' } }` **пропускает** их в листинги, счётчики и подборы, где Р39 запрещает. Все «листинговые» запросы спредят единый `IN_STOCK_WHERE` из `src/lib/rules/availability.ts` (`status = in_stock` **И** `quantity > 0`) — это query-близнец `availability()`. Страницы, где бронь/продано показываются со статусом (товар, Обране, Порівняння, «Ви дивилися»), фильтруют `not_equals: 'hidden'` и пересчитывают `availability()` на карточку. Карточку закрывают по `availability` (не по `status`: он сводит `reserved` к `in_stock`). (Поймано 27.11: reserved показывался купуемым в каталоге/Обраному; регресс-тест — `availability.test.ts` «IN_STOCK_WHERE».)
