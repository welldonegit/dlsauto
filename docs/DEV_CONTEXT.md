# DLSAuto — контекст разработки (версия 1.2, 30.10.2026)

Источник правды по разработке. Читать вместе с PROJECT_CONTEXT.md (продукт и дизайн) и DESIGN_RULES.md. Токены дизайна живут в коде (`src/app/globals.css`); `docs/DESIGN_TOKENS.md` генерируется из него в этапе 1. Приоритет при конфликте: явная просьба в чате → этот файл → PROJECT_CONTEXT.md → DESIGN_RULES.md.

Язык интерфейса — украинский. Код, комментарии, коммиты, имена — английский. Общение в чате — русский.

---

## 1. Что строим

Интернет-магазин б/у автозапчастей DLSAuto (Запоріжжя + пункт в Дніпрі). ~1200 деталей, каждая в одном экземпляре. Каналы продаж: сайт, Prom.ua, avto.pro, OLX. Учёт остатков и заказов — в KeyCRM. Личного кабинета нет. Дизайн готов в Claude Design, экспорт — спецификация, не исходник.

Ключевые свойства, которые влияют на архитектуру:
- Каждый товар уникален → нет количества, есть состояние «в наявності / продано». Двойная продажа между сайтом и Prom — главный риск, см. §6.
- Поиск — главный вход: по названию детали + авто, по OEM, по артикулу, «всё с моей машины».
- Большинство покупателей — самовывоз. Два пункта выдачи, масштабируется на N.
- Проданные товары живут на сайте со статусом «Продано» и альтернативами (SEO).

| Сеть | Cloudflare: DNS, CDN, WAF. Кэш картинок и статики на edge |

## 3. Принципы кода

1. **Дизайн-система раньше страниц.** Сначала токены → примитивы → составные компоненты → страница `/ui` → страницы. Новый стиль на странице = сигнал вернуться в компоненты, не писать локально.
2. **Экспорт Claude Design — спецификация.** Из него берутся значения (токены, размеры, тексты), код переписывается.
3. **Один компонент — один стиль — все размеры.** Кнопка: primary / secondary / tertiary × S / M / L. Круглая стрелка: S / XL. Чип, таб-пилюля, карточка товара, карточка модели, карточка-документ, тост, корзина-панель, быстрый просмотр, sticky buy bar — по PROJECT_CONTEXT.md §3.
4. **Server Components по умолчанию.** Клиентские — только интерактив: корзина, избранное, поиск, анимации, слайдеры.
5. **Анимации — только transform/opacity**, без SVG-фильтров в кадре, с `prefers-reduced-motion`.
6. **Все внешние интеграции — через один модуль `src/integrations/<name>`** с типизированным клиентом, ретраями, логированием и тестами на моках. Никаких прямых fetch из компонентов.
7. **Идемпотентность.** Вебхуки и опросы могут прийти дважды — каждая операция синхронизации безопасна при повторе.
8. **Ошибки интеграций не ломают сайт.** KeyCRM недоступен — заказ сохраняется локально со статусом `pending_sync`, воркер досылает.
9. **Чистые #000/#FFF не используются**, размеры — токенами, см. DESIGN_RULES.md.

### 3.1. Унификация, не редизайн

Экспорт Claude Design содержит плавающие значения (один и тот же элемент с разными радиусами, отступами, размерами шрифта). Задача этапа 1 — свести их к одному канону, **не меняя дизайн структурно**.

Процедура, строго по порядку:
1. **Аудит.** Скриптом собрать инвентарь всех значений экспорта: размеры и веса шрифтов, межстрочные, отступы, радиусы, тени, цвета, высоты контролов, пропорции изображений — с местами и частотой.
2. **Канон.** Для каждого параметра эталон выбирается по приоритету: PROJECT_CONTEXT.md → самое частое значение в экспорте → ближайшая ступень шкалы DESIGN_RULES.md. Выдумывать значения запрещено. Результат — токены в `globals.css` и сгенерированный `docs/DESIGN_TOKENS.md`.
3. **Таблица расхождений** на утверждение владельцу: элемент, где, какие значения встречались, выбранный канон, основание. Пока таблица не утверждена — компоненты не пишутся.
4. Код компонентов по утверждённому канону.
5. **Сверка**: `/ui` и ключевые страницы рядом со скриншотами Claude Design, десктоп и мобайл. Расхождения — снова таблицей.

Граница:
- **Можно (унификация):** значения — размер, отступ, радиус, цвет, вес, тень, длительность анимации. Свести похожие к одному.
- **Нельзя (структура):** состав элементов, их порядок, раскладка, сетка, пропорции блоков, поведение, тексты, распределение по колонкам. Если ради унификации хочется что-то переставить — это вопрос владельцу, а не решение.

## 4. Модель данных (Payload collections)

**brands** — name, slug, logo (mono + color), sortOrder, published.

**models** (поколение) — brand, name («L200»), generation («IV», «WK», опц.), yearFrom, yearTo (null = по сейчас), bodyType (`pickup` | `suv` | `passenger`, только для группировки секций главной, в UI не выводится), twinName («Pathfinder», опц.), donorPhoto (опц., не выводится пока нет у всех), sortOrder, published.
Вычисляемые: partsCount (товары в наличии).

**categories** — name, slug, photo, description, seoTitle, seoDescription, sortOrder, published. Плоские, один уровень.

Локализуемые поля (uk/ru): у brands — нет; у models — нет; у categories — name, description, seo*; у products — name, description, condition (текст), seo*; у pages — все текстовые поля блоков; у settings — текстовые условия и описания каналов. Слаги общие для обоих языков.

**products** — поля:
- sku (артикул KeyCRM, уникальный, обязателен для синхронизации), promId (опц.), oem[] (один или несколько OEM-номеров, нормализованные копии для поиска), name, slug, category, model (донор), description (richText), condition (состояние: текст + фото дефектов), photos[] (порядок, первое — главное, видео последним), price, discountPercent (опц.), featured (бегущая рамка, независимо от скидки), status (`in_stock` | `sold` | `hidden`), pickupPoint (где лежит), seasonalDecor (bool — показывать праздничную наклейку, когда активен сезон), alsoFits[] (модели, опц.), boughtTogether[] (вручную), alternatives[] (вручную), seoTitle, seoDescription, createdAt.
- Вычисляемые: isNew (createdAt < 30 дней ИЛИ pinnedNew), fromSameCar (автоматически по model), salesCount.

**pickup-points** — name («Запоріжжя»), address, schedule, mapCoords, phone, isDefault.

**orders** — number, status (зеркало KeyCRM), keycrmId, items[] (product, price на момент), customer (name, phone, email), delivery (type `np` | `delivery` | `pickup`, warehouse/point, address), payment (type, prepaymentAmount, monopayInvoiceId, paid), totals, utm, comment, syncStatus (`pending` | `synced` | `failed`), createdAt. В админке — только чтение + ссылка в KeyCRM.

**leads** — заявки из форм: type (callback, ask-about-part, sto), name, phone, message, photo (опц.), product (опц.), utm, createdAt.

**banners** — полоса над шапкой: text (uk/ru), link (опц.), variant (из набора системы: dark / light / primary-tint), season (`any` | конкретный сезон), dateFrom, dateTo, dismissible, published, sortOrder. Показывается первый подходящий по сезону и датам; закрытие запоминается в localStorage по id баннера.

**reviews** — author, rating 1–5, text, photo (опц., одно изображение детали из отзыва), product (опц.), published (модерация), createdAt. Средняя считается по published.

**pages** — контент страниц блоками (главная, о компании, контакты, оферта, политика, 404). Каждый блок — свой тип с полями; пустой блок не рендерится. Порядок блоков — drag-and-drop.

**settings** (global) — телефоны, email, мессенджеры, описания каналов (подписи под Telegram / Viber / телефоном на «Контактах», локализуемые), соцсети, рейтинг и количество отзывов на Prom (числа), ссылки на маркетплейсы, минимальный заказ (500), время отправки в день заказа (15:00), условия предоплаты, блок «Приймаємо», реквизиты ФОП, KeyCRM base URL (для ссылок на заказы), season (`none` | `halloween` | `new_year` | `easter`, с датами начала/конца и ручным переключателем).

**media** — файлы, sharp-варианты: thumb 400, card 800, gallery 1600, WebP.

## 5. Бизнес-правила

- **Мин. заказ 500 ₴.** Прогресс-бар в корзине, чекаут недоступен ниже порога.
- **Отправка:** заказ подтверждён до 15:00 (Europe/Kyiv) → «Сьогодні», после — «Завтра», в воскресенье → «У понеділок». Считается на сервере по текущему времени, учитывает график Пн–Сб.
- **Новинки:** `isNew` = создан менее 30 дней назад или закреплён вручную. Блок на главной — 15 самых новых в наличии, автоматически, с табами по категориям.
- **Скидка** `discountPercent` → бейдж «−N%» primary. **Featured** → бегущая красная рамка. Независимые поля.
- **Продано:** страница живёт, карточка со статусом «Продано», кнопка secondary «Запитати аналог», блок альтернатив. В каталоге проданные не показываются (опция фильтра «показати продані» — нет).
- **Пункт выдачи:** информация на карточке и странице товара («В наявності, Дніпро»). В чекауте один выбор пункта на весь заказ; если часть деталей в другом пункте — информационная строка, заказ не дробится.
- **Предоплата:** сумма из settings (ориентир 200 ₴) для габаритных / по флагу товара — уточняется у клиента. monoPay-инвойс на сумму предоплаты или полную.
- **Секции «на пікапи» / «на позашляховики»:** товары по bodyType модели + ручное закрепление.
- **Избранное, сравнение, просмотренные, корзина** — localStorage с версией схемы; корзина живёт 7 дней. **Выбранное авто** — cookie (нужна на сервере для «Підходить на ваше авто»). **UTM** — cookie first-touch, 30 дней.
- **«Підходить на ваше авто»** = product.model совпадает с выбранным авто (или входит в alsoFits). Без внешних баз совместимости.
- **Языки:** uk по умолчанию без префикса, ru под `/ru`. Переключатель в тёмной полосе хедера, выбор — в cookie. Автоматического редиректа по языку браузера нет. Письма, Telegram, админка — украинский. Fallback: если ru-поле пустое, показывается uk. Импорт из Prom: если текст только ru — машинный перевод в uk с флагом «перевірити» в админке.
- **Праздничный режим:** `settings.season` включается по датам автоматически, можно переключить вручную. Когда сезон активен: глобальный эффект (летучие мыши, снег и т. п.) — один раз за сессию, canvas/CSS, только transform/opacity, не грузится при неактивном сезоне и при `prefers-reduced-motion`; на товарах с `seasonalDecor` — наклейка, соответствующая сезону (тыква, шапка эльфа, писанка), SVG-набор в коде. Сезон выключился — наклейки исчезли, флаги на товарах остались до следующего года. Наклейка, бейдж скидки и бегущая рамка — разные слоты карточки, совместимы. В админке: массовое действие «Позначити святковою наклейкою / зняти» на выбранных товарах и фильтр «з наклейкою». Баннер над шапкой — коллекция banners, привязка к сезону и датам. Внешний вид состояний и баннера — задача Claude Design (дизайн-бэклог).

## 6. Интеграции и синхронизация остатков

**Владение данными:** KeyCRM — мастер по наличию и заказам. Сайт — мастер по контенту. Prom — канал, который кормит KeyCRM. Связка товаров — по `sku`.

**Поток «продажа на сайте»:**
1. Чекаут → серверный action: проверить `status = in_stock` локально.
2. Синхронно запросить KeyCRM по sku: остаток > 0? Нет → ответ «Цю деталь щойно забрали», заказ не создаётся.
3. Создать заказ в KeyCRM (товары, доставка, оплата, UTM). Получить keycrmId.
4. Локально: product.status = sold, order.syncStatus = synced.
5. Параллельно, не блокируя ответ: Prom API — товар «немає в наявності»; Telegram-уведомление; email покупателю.
6. Если KeyCRM недоступен: заказ сохраняется локально с `pending_sync`, товар помечается sold, воркер повторяет отправку каждую минуту; менеджер получает в Telegram пометку «не синхронизирован».

**Поток «продажа на Prom»:**
- KeyCRM забирает заказы с Prom ~раз в 10 минут (документация KeyCRM) — медленно.
- Поэтому воркер сам опрашивает Prom API по новым заказам каждые 60 с и помечает товары sold немедленно.
- Дополнительно KeyCRM шлёт вебхук изменения остатков (sku, in_stock) — обрабатываем как подтверждение.

**Вебхуки KeyCRM → сайт:**
- `/api/webhooks/keycrm/stock` — изменение остатков: in_stock 0 → sold, > 0 → in_stock.
- `/api/webhooks/keycrm/order` — триггер на смену статуса заказа: обновить order.status, при оплате — paid.
- Подпись/секрет в заголовке или query, проверка обязательна; идемпотентность по event id или (sku, timestamp).

**Страховка:** ночная полная сверка остатков KeyCRM ↔ сайт, расхождения — в лог и Telegram.

**Nova Poshta API** — города и отделения с автокомплитом, кэш справочников в БД, обновление ночью.
**Delivery API** — то же.
**monoPay** — создание инвойса, вебхук оплаты, проверка подписи.
**Telegram** — бот в групповом чате: заказы и заявки, с UTM одной строкой и ссылкой в админку.
**Email покупателю** — подтверждение заказа и смена статуса (провайдер — Resend или SMTP, решается в этапе 5).
**Импорт из Prom** — одноразовый скрипт из YML/XLSX-выгрузки: товары, фото, категории → черновики в Payload для сверки.

## 7. Поиск

Postgres: `tsvector` по name + description (украинская конфигурация или simple + unaccent), `pg_trgm` GIN по name, по нормализованным OEM и sku (убраны пробелы, дефисы, точки, нижний регистр). Автокомплит с 3 символов, debounce 150 мс, ответ < 100 мс, до 8 подсказок: товары, модели, категории. Точное совпадение OEM/sku → редирект сразу на товар. Страница результатов — каталог с чипами разбора запроса, см. PROJECT_CONTEXT.md.

## 8. SEO — заложить с первого дня

- URL: `/catalog/<category>`, `/catalog/<category>?brand=&model=` (фильтры — query, canonical на чистую категорию), `/brand/<brand>`, `/brand/<brand>/<model>`, `/product/<slug>-<sku>`, `/search?q=`.
- Языки: `hreflang` uk/ru + `x-default` на uk на каждой странице; `/ru` — полноценные страницы, не параметр. Sitemap включает оба языка.
- Один H1 на странице, мета из полей seoTitle/seoDescription с fallback-шаблонами.
- schema.org: Product + Offer (availability по статусу), BreadcrumbList, Organization, FAQPage.
- sitemap.xml динамический (товары в наличии и проданные, категории, бренды, модели), robots.txt, `noindex` для поиска, чекаута, избранного, сравнения.
- Проданные — остаются 200 со статусом «Продано».
- Полная SEO-итерация — этап 8.

## 10. Правила работы Claude Code

1. Перед задачей прочитать этот файл и остальные в `docs/`: PROJECT_CONTEXT.md, DESIGN_RULES.md (и DESIGN_TOKENS.md, когда появится после этапа 1). Промпт текущего этапа — в `docs/stages/`.
2. Работа ведётся прямо в ветке `stage`. `main` — релизная ветка, обновляется только мержем из `stage` по команде владельца. Фича-веток нет.
3. Коммиты — Conventional Commits, на английском.
4. TypeScript strict, ESLint + Prettier, без `any` без комментария-обоснования.
5. Тесты: unit для бизнес-правил (дата отправки, новинки, нормализация OEM) и для интеграций на моках; e2e (Playwright) для чекаута и поиска — с этапа 5.
6. Не добавлять зависимости без необходимости; каждая новая — строка в README с причиной.
7. Секреты только в env; `.env.example` поддерживается актуальным.
8. UI-тексты — только украинский, из PROJECT_CONTEXT.md; без lorem ipsum и выдуманных сущностей (категорий, моделей, цифр).
9. В конце каждой задачи — короткий отчёт: что сделано, что не сделано и почему, что проверить руками.
10. Если задача противоречит этому файлу или DESIGN_RULES.md — спросить, прежде чем нарушать.
11. Любое расширение модели данных сверх §4 (новое поле/коллекция/глобал) — только с согласованием и **сразу с правкой §4 в том же коммите**. Модель и §4 не должны расходиться.
12. Перед задачей просмотреть раздел [«Известные грабли — не повторять» в `CLAUDE.md`](../CLAUDE.md#известные-грабли--не-повторять). Новая пойманная ошибка — строка в этот раздел **в том же коммите, что и исправление**.

## 11. Открытые вопросы (не блокируют этапы 0–3)

- KeyCRM: частота передачи остатков в Prom; доступ к тестовому аккаунту.
- Prom: API-токен; лимиты запросов для опроса раз в минуту.
- monoPay: договор эквайринга, тестовый мерчант.
- Предоплата: фикс для всех габаритных или флаг на товаре; сумма.
- Днепр: склад или вторая разборка; адрес, график; перевозят ли между пунктами и за сколько.
- Фото: где лежат оригиналы, формат, качество.
- Реальный список категорий и топ-10 деталей по продажам.
- Кто ведёт заказы после создания — только KeyCRM (подтвердить).
- Email-провайдер.
- Дизайн состояний праздничного режима (глобальный эффект, наклейка на карточке) — ждёт макета в Claude Design.
