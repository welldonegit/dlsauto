## 5. Проверка схемы §3 (новая): сценарии, дыры, гонки

Оговорка: детальной «таблицы §3.2» в плане нет (§3 не переписан — см. §3-выше). Сценарии ниже построены по схеме §0 Р1–Р5 + §3 + потоку DEV_CONTEXT §6. Актуальная модель владения:
- **KeyCRM — единственный мастер остатка.** Отдаёт остаток на Prom и шлёт вебхук остатков на сайт. Сайт Prom API по наличию не трогает (Р1).
- **Сайт** на свою продажу создаёт заказ в KeyCRM (DEV_CONTEXT §6 шаг 3) и локально метит `sold` (шаг 4); новый товар сразу заводит в KeyCRM через API с остатком (Р4).
- **Воркер** опрашивает заказы Prom раз в 60 с (Р2), чтобы пометить `sold` быстрее, чем KeyCRM (~10 мин).

### Сценарий 1 — две продажи одной детали (сайт + Prom) в окне 1–10 мин
- t0: деталь в наличии везде.
- t1: покупатель A оформляет на **сайте** → сайт синхронно спрашивает KeyCRM «остаток>0?» (DEV_CONTEXT §6 шаг 2) → да → создаёт заказ в KeyCRM → KeyCRM резервирует/списывает → локально `sold`.
- t1+δ: покупатель B оформляет на **Prom** (листинг ещё «в наявності», т.к. KeyCRM→Prom-пуш не мгновенный) → заказ уходит в Prom.
- **Дыра/гонка:** окно = задержка **KeyCRM → Prom** (пуш остатка). Пока KeyCRM не обновил листинг Prom, деталь на Prom доступна. Сайт тут бессилен (Р1 запрещает сайту трогать Prom). Итог — две продажи одной детали.
  - *Насколько велико окно* — зависит от скорости KeyCRM→Prom. Док говорит «остатки відправляються на джерело одразу» (§6, п.5), но SLA по времени нет; сайтовую продажу KeyCRM узнаёт сразу (заказ создаёт сайт), продажу на Prom — после опроса. Если на практике минуты — риск реален (вопрос клиенту 3).
  - *Митигации:* (а) предоплата/подтверждение менеджером (уже в продукте) делают двойную продажу не фатальной; (б) при продаже на сайте, помимо заказа в KeyCRM, **разрешить сайту разово дёрнуть Prom API `presence=нет`** именно для снятия с Prom — это осознанное исключение из Р1 ради скорости (KeyCRM потом подтвердит тем же значением, гонки нет, т.к. оба пишут «нет»). Рекомендую вернуть этот шаг **только на снятие** (не на возврат в наличие). Вопрос владельцу 1.

### Сценарий 2 — отмена заказа после пометки «Продано»
- Заказ отменён/удалён в KeyCRM → резерв освобождается → `in_stock` растёт → вебхук остатков → сайт `sold → in_stock` (DEV_CONTEXT §6 обрабатывает «>0 → in_stock»). KeyCRM возвращает остаток и на Prom.
- **Дыры:** (1) нужно подтвердить, что отмена/освобождение резерва **шлёт вебхук** (Р2 перечисляет триггеры «смена статуса с резервом/списанием» — отмена должна попадать; §4-таблица проверяет). (2) SEO: страница была «Продано» — возврат в наличие корректен, но если на неё успели сослаться как на проданную, ничего страшного (200 остаётся). (3) Если деталь продали на **сайте** (не через KeyCRM-заказ, а вручную в админке) — освобождения не будет; но по схеме сайт всегда создаёт заказ в KeyCRM, так что кейс краевой.
- **Гонка возврата:** если одновременно пришли вебхук «in_stock=1» (отмена) и опрос Prom «продано» — нужна идемпотентность по `offer_id`+значению и «последний выигрывает по времени события», иначе качели. Заложить в обработчик.

### Сценарий 3 — количество > 1
- KeyCRM шлёт вебхук с `in_stock` = число и `in_reserve`; доступно = `in_stock − in_reserve` (Р2).
- **Дыра:** DEV_CONTEXT §6-вебхук сейчас бинарный (0→sold, >0→in_stock). При `quantity>1` сайт должен хранить и показывать **число** («В наявності, 3 шт»), а `sold` ставить только при доступном 0. Обработчик и поле `quantity` надо спроектировать на число, а не на флаг. Зависит от ответа клиента (вопрос 6): если количество — «устаревшие цифры» и всё = 1, бинарной логики достаточно.
- **Корзина:** §5 обещает «выбор числа в корзине (этап 5)» — тогда при оформлении сайт должен резервировать N штук в KeyCRM, и вебхук уменьшит доступное, не обнуляя. Согласованно, но требует, чтобы заказ в KeyCRM уходил с количеством.

### Сценарий 4 — сбой/пропуск вебхука остатков
- Если вебхук не дошёл (сеть, 5xx, downtime сайта) — остаток на сайте устаревает → риск продать проданное.
- **Подстраховка в плане:** Р2 — «ночная полная сверка через API» + опрос заказов Prom раз в 60 с. Для товаров, продаваемых на Prom, 60-с опрос ловит продажу быстро; для чисто-сайтовых и ручных правок склада — до суток рассинхрон (до ночной сверки).
- **Рекомендация:** (1) сделать приём вебхука идемпотентным и подтверждать 2xx только после записи; (2) KeyCRM обычно **ретраит** недоставленные вебхуки — проверить политику ретраев (§4-таблица); (3) помимо ночной — лёгкая периодическая сверка (напр. раз в 15–30 мин) по товарам «в наявності», чтобы окно рассинхрона было минутами, а не сутками. Нагрузка укладывается в лимит API (вопрос лимита — §4).

### Сценарий 5 — новый товар, ещё не связанный KeyCRM с публикацией Prom
- Сайт публикует товар → заводит в KeyCRM через API с остатком = quantity (Р4) → фид отдаёт товар на Prom → Prom создаёт публикацию → KeyCRM должен **связать** её с уже существующим оффером по SKU.
- **Главная дыра — СНЯТА документацией** (§6, п.4). KeyCRM при совпадении SKU **не создаёт дубль, а линкует** публикацию Prom к существующему офферу: «If a publication has the same SKU… a new product will not be created and the publication will be linked to the existing product». Условие — **в публикации Prom должен быть SKU**, то есть фид обязан отдавать `sku` как `vendorCode` (KeyCRM создаёт/линкует только из публикаций, где SKU есть у источника). Значит порядок Р4 рабочий: сайт заводит оффер в KeyCRM по sku → фид отдаёт тот же sku на Prom → KeyCRM связывает публикацию по sku, остаток не расщепляется.
- **Остаточный нюанс:** вебхук остатков не шлёт **начальные** остатки (§6, п.1d) — только изменения. Поэтому при заведении нового оффера сайт сам ставит остаток через API (`offersStocksUpdate`), а не ждёт вебхука; и при подключении интеграции нужна **разовая загрузка** остатков (Р2 это уже учитывает). Порядок: создать оффер + выставить остаток через API → включить отдачу на Prom → дальше жить на вебхуках/сверке.

### Сводка дыр схемы
1. **Окно двойной продажи** = латентность KeyCRM→Prom (сценарий 1). Док говорит «отправляется сразу», но SLA по времени нет (§6). Митигация — предоплата/подтверждение (уже в продукте) + опционально разрешить сайту разово снять с Prom через API (исключение из Р1).
2. ~~Дубль оффера по SKU~~ — **снято** (§6, п.4): KeyCRM линкует по SKU, не дублирует. Условие — фид отдаёт `sku` как `vendorCode`.
3. **Бинарный вебхук vs `quantity>1`** (сценарий 3) — доработать обработчик/поле `quantity`.
4. **Возврат резерва при отмене** шлёт вебхук (§6, п.6) — обработчик сделать идемпотентным (сценарий 2).
5. **Пропуск вебхука** → рассинхрон для чисто-сайтовых товаров (сценарий 4). Вебхук не шлёт начальные остатки (§6, п.1d) — обязательна разовая загрузка при подключении + частая сверка (15–30 мин) сверх ночной.
