## 0. Решения после ревью (20.11.2026)

**Р1. Остаток — один источник правды: KeyCRM** (закрывает B8). KeyCRM сам отдаёт остатки на Prom (штатная передача остатков на маркетплейсы, связь с публикациями по SKU). Сайт **не** меняет наличие на Prom через API. Шаг 5 DEV_CONTEXT §6 («Prom API — товар немає в наявності») убрать.

**Р2. Вебхук остатков у KeyCRM есть — B6 отклонён.** Справка KeyCRM: «Передача змін залишків на вебхук» (help.keycrm.app/en/products-and-warehouse/transferring-balance-changes-via-webhook). Шлёт при: смене статуса заказа с резервом/списанием, оприбуткуванні/інвентаризації, импорте, изменении через API или вручную. Тело — массив `{offer_id, sku, in_stock, in_reserve}`; доступно = `in_stock − in_reserve`. Условия: включён складской учёт; начальные остатки не шлёт (только изменения). Ревью смотрело только раздел вебхуков автоматизации (заказы/лиды).
Схема: вебхук → сайт (`/api/webhooks/keycrm/stock` остаётся) + ночная полная сверка через API + разовая загрузка остатков при подключении. Опрос заказов Prom API раз в 60 с **остаётся**, но только чтобы сразу пометить «Продано» на сайте (KeyCRM забирает заказы Prom ~раз в 10 мин). Лимит API KeyCRM: справка «How to send stock balances…» — 60 запросов/мин на ключ, ревью — 20/мин; перепроверить, проектировать под ≤ 20.

**Р3. Артикул один на всё.** sku = одна физическая деталь, **одинаковый** на сайте, в KeyCRM (SKU оффера) и на Prom (`Код_товару`) — KeyCRM связывает товар с публикациями маркетплейсов по SKU. Дубли на Prom (212 кодов / 583 строки) до запуска перенумеровать (на Prom — xlsx-импортом, в KeyCRM — импортом/API). Новые товары — sku генерирует сайт.

**Р4. Новый товар появляется в KeyCRM сразу, не через Prom.** При публикации товара на сайте воркер создаёт товар/оффер в KeyCRM через API (sku, название, цена) и ставит остаток = quantity. Иначе до подтягивания из Prom в KeyCRM остаток 0 → вебхук «0» → товар на сайте станет «Продано». Prom получает товар фидом и связывается с KeyCRM по SKU. *Проверить по API KeyCRM: создание товара + установка остатка (`/offers/stocks` или аналог), что произойдёт, когда KeyCRM подтянет ту же публикацию из Prom (дубль или связка по SKU).*

**Р5. Фид Prom: `<offer id>` = sku** (закрывает B7). Существующим 1407 товарам до первого фида проставить «Ідентифікатор_товару» = sku xlsx-импортом Prom (сопоставление по «Унікальний_ідентифікатор»). Проверить на 5–10 товарах в кабинете клиента. Если Prom так не умеет — фолбэк из ревью: `offer id` = `promId` для старых товаров. Интервалы фида (цена/наличие ~4 ч, новые товары ~раз в сутки) приемлемы: наличие идёт через KeyCRM сразу; клиенту сказать, что новый товар появится на Prom на следующий день.

**Р6. Характеристики** (R1): значения характеристик категории — отдельные типизированные значения по `specTemplate` категории; панель карточки/quick-view/страницы собирается вычисляемо: Стан → характеристики категории → Пробіг (донор) → Авто-донор. Свободный `specs[]` остаётся как «Додатково» — туда идут несопоставленные характеристики Prom.

**Р7. Категория выводится из типа** (R3): хук при выборе `partType`, поле `category` в админке только для чтения.

**Р8. Донор отдельно от модели** (R2): коллекция `donors`; `model` = поколение (совместимость, метка на карточке, «підходить на ваше авто»). «Ще з цього авто» — по `donor`, фолбэк по `model`.

**Р9. Новинки по `receivedAt`** (R5). Импорт Prom ставит `receivedAt` пустым.

**Р10. Матрица расположения** (R6). Расположение раскладывается на оси: вісь (передня / задня / —), бік (ліва / права / пара / —), сидіння (водійська / пасажирська). Две позиции совместимы, если по каждой оси значения равны или у одной из них «—»; «пара» совместима с ліва и права в обе стороны; водійська/пасажирська совместимы только с равным значением. Для типов с правилом `none` расположение в подборе не участвует. Покрыть unit-тестами.

**Р11. Twin-модели** (R7): Navara D40 и Pathfinder R51 — **отдельные** записи `models`. Перёд у них общий, зад разный (пикап / SUV) — автосклейка дала бы ложное «підходить» на кузов. Совместимость — через `alsoFits` (при импорте Prom — из «Сумісність з моделлю»). Так уже устроено у Ranger / BT-50. Следствие: в «Деталі для вашого авто» и мега-меню две карточки вместо одной — это контент, не дизайн.

**Р12. Модели** (B9): до отправки шаблона клиенту собрать реальный список поколений по 31 группе Prom + совместимости (черновик — Claude Code, подтверждают владелец и клиент) → коллекция `models` → список в шаблоне. Позже в админке шаблон генерируется из коллекции. Марки — те, что реально есть в каталоге; Great Wall остаётся (4 товара).

**Р13. Разметка исправлена** (B2–B5): «бажано» не флагуется; водійська/пасажирська извлекаются; дверні карти → Салон; ляда / двері багажника → «Борт / кришка багажника»; добавлены «Радіатор EGR» в тип EGR и тип «Щуп масляний». Итог: OK 1354, «Перевірити» 53 (51 — нет обязательной стороны), 104 типа.

**Р14. Плашки на странице товара** (D1): по дизайну под OEM — «В наявності, N шт» (status + quantity), «Гарантія N днів» (`warrantyDays`, обязательное поле товара, задаёт клиент; 0 — плашка не показывается), «Перевірено» (показывается, когда `conditionLabel` = «Б/в, перевірений»). Отдельного поля `checkMethod` нет — колонка «Перевірка» убрана из шаблона, это дублировало «Стан». `settings.defaultWarrantyDays` не нужен.

**Р15. Поисковые синонимы** (D2): колонку в шаблон не добавляем. Общий словарь синонимов в админке (этап 4): «навара» → Navara, «гур» → насос ГПК, «приборка» → панель приладів; стартовое наполнение — из `Пошукові_запити` Prom. Работает для всех товаров, включая новые. Пер-товарный `searchKeywords` — только для импортированных с Prom.

**Р16. Импорт** (G): Prom — разовый скрипт до запуска, фото в воркере, 2–3 параллельно. Импорт таблицы — UI в админке, нужен к моменту, когда клиент начнёт вносить новые товары.

## 1. Принципы

1. **Клиент вводит только то, что знает он один.** Всё, что можно вычислить (категория Prom-товаров, годы, рекомендации, новинки, SEO, поисковые синонимы), сайт считает сам. Новое поле на сайте не должно превращаться в «заполните ещё 4 колонки для 500 товаров».
2. **Ключи — из списков, не из текста.** Тип детали, расположение, марка, модель, стан, проверка — выпадающие списки. Разбор названий — только подсказка для импорта Prom, не источник правды.
3. **Только детерминированные правила.** Каждое правило записано в DEV_CONTEXT §5 и покрыто unit-тестами на фикстурах из реальной выгрузки.
4. **У каждого правила — фолбэк**, и блок никогда не бывает пустым или нелепым: не набралось — блок скрыт.
5. **Любой автоматический результат виден и правится в админке.** Ручная правка важнее автоматики и не перезаписывается при пересчёте.
6. **Всё сомнительное — в очередь «Перевірити»**, не на витрину молча.

## 2. Что показало исследование выгрузки Prom

Факты (пересчитать скриптом при ревью, не на глаз):

- 1407 товаров. Названия и описания есть на обоих языках (ru + uk) у всех.
- **`Код_товару` не уникален.** Заполнен в 1390 строках, уникальных значений 1019; 212 кодов повторяются в 583 строках (пример: код `5155373` — пять капотов с ценами 3999–8500). В 1205 случаях (1211 после нормализации) `Код_товару` = «Код запчастини» (OEM). То есть у клиента артикул ≈ OEM-номер, а не номер экземпляра.
- **Уникальный ключ на Prom — `Унікальний_ідентифікатор`** (1407 из 1407 уникальны).
- **Количество > 1** в 318 строках (до 30 шт.). Противоречит правилу «каждая деталь в одном экземпляре».
- Наличие: `+` 1219, `-` 135, `!` 52, `2` — 1. Значение `!` у клиента неизвестно.
- Группы клиента на Prom — в основном модели («Nissan navara pathfinder r51»), а не категории. Категорий как таковых нет. Есть **рубрика каталога Prom** (`Посилання_підрозділу`, 137 значений) — мелкая и местами ошибочная (фара в «Кузові», редуктор в «Оптиці»).
- Совместимость: «Сумісність з маркою» 1357, «з моделлю» 1229 — через `|`, без поколения. Поколение есть только в названии группы.
- Характеристики — длинный хвост из ~60 названий, большинство встречается 1–10 раз. «Стан» почти всегда просто «Вживаний» (описания дефектов нет).
- Фото: ссылки `images.prom.ua`, 1–10 на товар через запятую; 33 товара без фото.
- Вес / габариты заполнены в 62 / 22 строках. SEO-заголовки — в 1 строке. «Де знаходиться товар» — только «Запоріжжя», 663 строки.
- `Пошукові_запити` ru/uk заполнены в 1369 строках — готовые синонимы и сленг («навара д40»).
- Описания — HTML с одинаковым шаблонным текстом («Наші переваги…», «Перед замовленням зв'яжіться…») и inline-стилями.
- Прочее: `Ціна_від = +` в 74 строках, валюта USD в 1 строке, единица «комплект» 21 / «пара» 2.

## 3. Поток данных и владение (предложение)

```
Админка сайта (контент) ──фид YML──▶ Prom ──интеграция KeyCRM──▶ KeyCRM (остатки, заказы)
        ▲                                                                │
        └──────────── вебхуки / опрос: остатки, статусы заказов ◀────────┘
```

- **Сайт — мастер контента**: название, описание, фото, характеристики, совместимость, цена. Новые товары заводятся **только** в админке (вручную или импортом таблицы).
- **KeyCRM — мастер остатков и заказов** (как в DEV_CONTEXT §6).
- **Prom — канал продаж.** Получает товары с сайта через YML-фид по ссылке (Prom забирает по расписанию). Наличие на Prom меняет **только KeyCRM** (Р1); новый товар сайт сразу заводит в KeyCRM через API (Р4).
- **Правило для клиента:** на Prom товары руками не редактировать — правка затрётся следующим обновлением фида.

**Не проверено и требует ревью / вопроса клиенту:**
- связан ли сейчас Prom с KeyCRM и по какому ключу (артикулы на Prom не уникальны — §2);
- как KeyCRM получает каталог Prom (автоматически / настройка / вручную);
- как часто Prom обновляет импорт по ссылке, ограничения тарифа клиента;
- как Prom сопоставляет товары фида с уже существующими 1407 (по какому полю) — риск дублей;
- есть ли у KeyCRM API создания/обновления товаров (альтернатива цепочке через Prom).

## 4. Артикулы

- **sku = одна физическая деталь, уникальный.** OEM — отдельное поле `oem[]`, артикулом не является.
- **Новые товары:** артикул выдаёт сайт при создании (формат вида `DLS-000123`), дальше он уходит на Prom и в KeyCRM без изменений. Альтернатива — брать из KeyCRM, если там уникальный и клиенту так удобнее (ответ клиента на вопрос 1, §16).
- **Существующие товары Prom:** сохраняем `promId` (= `Унікальний_ідентифікатор`). Если в KeyCRM уникальный артикул — берём его как sku; если нет — генерируем sku, связка с Prom по `promId`. `Код_товару` → в `oem[]`, если похож на OEM.
- Фото в шаблоне именуются по артикулу (`DLS-000101_1.jpg`) — поэтому артикул должен быть уникален уже в таблице.
- На карточке товара сейчас подпись «Артикул: OEM 10102-…», на странице товара OEM и «Код» раздельно — подпись на карточке привести к странице товара (в ревью 3b).

## 7. Тип детали и расположение

- **Справочник типов** (`DLSAuto_dovidnyk_typiv.xlsx`): 104 типа, у каждого — категория и правило стороны:
  - `lr` — обязательно ліва/права (фари, ліхтарі, двері, крила, дзеркала, супорти, піввісі, цапфи, торсіони…);
  - `fb` — обязательно передня/задня (бампер, амортизатор, гальмівний диск);
  - `any` — желательно (скло, важіль, сидіння);
  - `seat` — водійська/пасажирська (подушка безпеки);
  - `—` — не нужно.
- **Расположение** — одно поле со списком: передня ліва / передня права / задня ліва / задня права / ліва / права / передня / задня / пара (ліва + права) / водійська / пасажирська / —.
- **Новые товары:** тип и расположение — выпадающие списки, обязательны по правилу типа. В админке тип подставляется подсказкой из названия, менеджер подтверждает.
- **Товары Prom:** тип и расположение — из разметки (разбор названия по словарю, приоритет — самое раннее совпадение, при равенстве — самое длинное).
  - Замер (v2, после правок Р13): тип распознан у 1405 из 1407; статус OK — 1354 (96%); «Перевірити» — 53 (4%): 51 — нет обязательной стороны («Цапфа в зборі», «Торсіон Ford Ranger»), 2 — тип не распознан.
  - Точность на случайной выборке 100 OK — 1–2 ошибки. Словарь подогнан на этих же названиях — на новых названиях будет хуже, поэтому для новых товаров только списки.
- Справочник типов — коллекция в Payload (редактируется админом, связи для «З цим купують» — там же).

## 8. Характеристики по категориям

- У категории — шаблон характеристик (3–5 полей, тип: текст / число / список). Форма товара в админке показывает поля его категории. В шаблоне таблицы — колонки справа от «Примітка» на листе категории.
- Почти все необязательные. Обязательные: «Код двигуна» для типа «Двигун у зборі»; «Діаметр» + «PCD» для дисков; «Розмір шини» для шин.
- Черновик — лист «Характеристики» в справочнике: кузов — колір; двигун — код, об'єм, паливо; КПП/мости — привід, передатне число; оптика — тип лампи, коректор; шини/диски — діаметр, PCD, розмір шини, сезон, залишок протектора; салон — колір, матеріал.
- Общие значения показываются в «Характеристиках» карточки и страницы: Стан, затем характеристики категории, затем Пробіг (из донора) и «Авто-донор».

## 10. Доноры

- Донор — конкретная машина, с которой сняты детали. Ключ: **модель + «№ авто»** (метка, которой клиент различает машины).
- Год и пробег — необязательные, достаточно в одной строке; сайт подставляет всем деталям донора. Импорт: один № авто с разными моделями — ошибка; с разными годом/пробегом — предупреждение.
- Коллекция `donors` создаётся автоматически при импорте/создании товара; в админке — переименовать, объединить, разделить, добавить фото машины (одно на донора).
- Отклонено: группировка по «модель + год + пробег» без метки — опечатка делит машину на две, неизвестный пробег склеивает две машины.
- **«Ще з цього авто»**: товары того же донора в наличии, без текущего. Карточка донора — модель, год, пробег, «деталей у наявності N», фото (если есть). Фолбэк: нет донора или < 3 деталей в наличии → по модели («Ще на Ranger 2006–2012»).
- Пробег донора выводится в характеристиках двигателя/КПП.

## 11. Новинки

- Поле **дата поступления** (`receivedAt`), ставится автоматически при создании в админке и при импорте таблицы.
- Новинка = в наличии и `receivedAt` < 30 дней, или закреплена вручную. На главной — 15 самых свежих, табы по категориям.
- Товары, перенесённые с Prom при запуске, — `receivedAt` пусто → не новинки (иначе 1407 позиций станут «новыми» на месяц).
- Отличие от DEV_CONTEXT: там `isNew` от `createdAt` — заменить на `receivedAt`.

## 12. Альтернативи

Детали, которые можно купить вместо этой.
1. Тот же OEM (нормализованный) — та же деталь с другой машины.
2. Иначе: тот же тип + совместимое расположение (левая к левой; «пара» совместима с обеими) + совместимая модель (model совпадает или входит в `alsoFits`, в обе стороны).
3. Только в наличии, без текущего; сортировка: состояние (перевірений выше), затем цена. До 6.
4. Пусто → блок скрыт. Для проданного товара — главный блок страницы (с «Запитати аналог»).
5. Ручное закрепление в админке — выше автоматики.

## 13. З цим купують

Детали, которые берут в комплекте.
1. Таблица связей **типов** в справочнике (заполняется админом один раз, 30–50 строк): фара → фара другой стороны, повторювач, решітка; двигун → турбіна, ПНВТ, форсунки; важіль → важіль другої сторони…
2. Кандидаты: сначала с того же донора, затем с той же модели; только в наличии; до 3.
3. После запуска — статистика заказов: пары, купленные вместе ≥ N раз, поднимаются выше (этап 7).
4. Ручное закрепление — выше автоматики. Пусто → блок скрыт.
5. Отличие от DEV_CONTEXT: там `boughtTogether[]` и `alternatives[]` ручные — становятся ручными переопределениями поверх автоматики.

## 14. Импорт Prom (разово, до запуска)

1. Источник — xlsx-выгрузка + `DLSAuto_prom_rozmitka.xlsx`.
2. Ключ — `promId`. sku — по решению §4.
3. Название / описание: uk и ru из выгрузки. Описание: вычистить шаблонный текст и inline-стили; содержательная часть → «Опис стану» / описание.
4. Категория, тип, расположение — из разметки. «Перевірити» → очередь в админке.
5. Модель-донор — из группы Prom + «Сумісність з моделлю» (сопоставление с моделями сида — отдельная таблица соответствия, 31 группа).
6. OEM — из «Код запчастини», «MPN», `Код_товару` (если похож на OEM), нормализованные копии для поиска.
7. Характеристики Prom → характеристики категории, где совпадают (колір, об'єм двигуна, сторона, тип запчастини → оригінал/аналог); остальное → примечание.
8. `Пошукові_запити` ru/uk → скрытое поле `searchKeywords` (новое, участвует в поиске этапа 4).
9. Фото — скачать по ссылкам (с сервера, не из браузера), sharp-варианты.
10. Наличие: `+` → in_stock; `-` → решение клиента (sold со страницей для SEO или не переносить); `!` — уточнить.
11. Цена: `Ціна_від`, USD — в очередь «Перевірити».
12. SEO — по шаблону (тип + модель + годы).
13. `receivedAt` — пусто (не новинки).
