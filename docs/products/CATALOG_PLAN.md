# DLSAuto — план каталога и наполнения товарами (черновик для ревью)

Статус: **v6 — после трёх ревью, моделирования и правок клиента (Р51–Р55).** Решения — §0 (Р1–Р16 ревью 1, Р17–Р26 ревью 2, Р27–Р43 ревью 3, Р44–Р50 моделирование), они **важнее** остального текста при расхождении. Цель — до начала наполнения выстроить логику товаров так, чтобы клиенту не пришлось перезаполнять таблицу.

---

## 0. Решения после ревью (20.11.2026)

**Р1. Остаток — один источник правды: KeyCRM** (закрывает B8). KeyCRM сам отдаёт остатки на Prom (штатная передача остатков на маркетплейсы, связь с публикациями по SKU). Сайт **не** меняет наличие на Prom через API. Шаг 5 DEV_CONTEXT §6 («Prom API — товар немає в наявності») убрать.

**Р2. Вебхук остатков у KeyCRM есть — B6 отклонён.** Справка KeyCRM: «Передача змін залишків на вебхук» (help.keycrm.app/en/products-and-warehouse/transferring-balance-changes-via-webhook). Шлёт при: смене статуса заказа с резервом/списанием, оприбуткуванні/інвентаризації, импорте, изменении через API или вручную. Тело — массив `{offer_id, sku, in_stock, in_reserve}`; доступно = `in_stock − in_reserve`. Условия: включён складской учёт; начальные остатки не шлёт (только изменения). Ревью смотрело только раздел вебхуков автоматизации (заказы/лиды).
Схема: вебхук → сайт (`/api/webhooks/keycrm/stock` остаётся) + ночная полная сверка через API + разовая загрузка остатков при подключении. Опрос заказов Prom API раз в 60 с **остаётся**, но только чтобы сразу пометить «Продано» на сайте (KeyCRM забирает заказы Prom ~раз в 10 мин). Лимит API KeyCRM: справка «How to send stock balances…» — 60 запросов/мин на ключ, ревью — 20/мин; перепроверить, проектировать под ≤ 20.

**Р3. Артикул один на всё.** sku = одна физическая деталь, **одинаковый** на сайте, в KeyCRM (SKU оффера) и на Prom (`Код_товару`) — KeyCRM связывает товар с публикациями маркетплейсов по SKU. Дубли на Prom (212 кодов / 583 строки) до запуска перенумеровать (на Prom — xlsx-импортом, в KeyCRM — импортом/API). Новые товары — sku генерирует сайт.

**Р4. Новый товар появляется в KeyCRM сразу, не через Prom.** При публикации товара на сайте воркер создаёт товар/оффер в KeyCRM через API (sku, название, цена) и ставит остаток = quantity. Иначе до подтягивания из Prom в KeyCRM остаток 0 → вебхук «0» → товар на сайте станет «Продано». Prom получает товар фидом и связывается с KeyCRM по SKU. *Проверить по API KeyCRM: создание товара + установка остатка (`/offers/stocks` или аналог), что произойдёт, когда KeyCRM подтянет ту же публикацию из Prom (дубль или связка по SKU).*

**Р5. Фид Prom: `<offer id>` = sku** (закрывает B7). Существующим 1407 товарам до первого фида проставить «Ідентифікатор_товару» = sku xlsx-импортом Prom (сопоставление по «Унікальний_ідентифікатор»). Проверить на 5–10 товарах в кабинете клиента. Если Prom так не умеет — фолбэк из ревью: `offer id` = `promId` для старых товаров. Интервалы фида (цена/наличие ~4 ч, новые товары ~раз в сутки) приемлемы: наличие идёт через KeyCRM сразу; клиенту сказать, что новый товар появится на Prom на следующий день.

**Р6. Характеристики** (R1): значения характеристик категории — отдельные типизированные значения по `specTemplate` категории; панель карточки/quick-view/страницы собирается вычисляемо: Стан → характеристики категории → Пробіг (донор) → Авто-донор. Свободный `specs[]` остаётся как «Додатково» — туда идут несопоставленные характеристики Prom.

**Р7. Категория выводится из типа** (R3): хук при выборе `partType`, поле `category` в админке только для чтения.

**Р8. Донор отдельно от модели** (R2): коллекция `donors`; `model` = поколение (совместимость, метка на карточке, «підходить на ваше авто»). «Ще з цього авто» — по `donor`, фолбэк по `model`.

**Р9. Новинки по `receivedAt`** (R5). Импорт Prom ставит `receivedAt` пустым.

**Р10. Матрица расположения** (R6). Расположение раскладывается на оси: вісь (передня / задня / —), бік (ліва / права / пара / —), сидіння (водійська / пасажирська). Две позиции совместимы, если по каждой оси значения равны или у одной из них «—»; «пара» совместима с ліва и права в обе стороны; водійська/пасажирська совместимы только с равным значением. Для типов с правилом `none` расположение в подборе не участвует. Покрыть unit-тестами.

**Р11. Twin-модели** (R7): Navara D40 и Pathfinder R51 — **отдельные** записи `models`. Перёд у них общий, зад разный (пикап / SUV) — автосклейка дала бы ложное «підходить» на кузов. Совместимость — через `alsoFits` (при импорте Prom — из «Сумісність з моделлю»). Так уже устроено у Ranger / BT-50. Следствие: в «Деталі для вашого авто» и мега-меню две карточки вместо одной — это контент, не дизайн.

**Р12. Модели** (B9): до отправки шаблона клиенту собрать реальный список поколений по 31 группе Prom + совместимости (черновик — Claude Code, подтверждают владелец и клиент) → коллекция `models` → список в шаблоне. Позже в админке шаблон генерируется из коллекции. Марки — те, что реально есть в каталоге; Great Wall остаётся (4 товара).

**Р13. Разметка исправлена** (B2–B5): «бажано» не флагуется; водійська/пасажирська извлекаются; дверні карти → Салон; ляда / двері багажника → «Борт / кришка багажника»; добавлены «Радіатор EGR» в тип EGR и тип «Щуп масляний». Итог (с Р36, Р45, Р46): OK 1340, «Перевірити» 67 (54 — нет обязательной стороны, 11 — «ліва/права»: комплект или на обе стороны, 2 — тип не распознан), 107 типов.

**Р14. Плашки на странице товара** (D1): по дизайну под OEM — «В наявності, N шт» (status + quantity), «Гарантія N днів» (`warrantyDays`, обязательное поле товара, задаёт клиент; 0 — плашка не показывается), «Перевірено» (показывается, когда `conditionLabel` = «Б/в, перевірений»). Отдельного поля `checkMethod` нет — колонка «Перевірка» убрана из шаблона, это дублировало «Стан». `settings.defaultWarrantyDays` не нужен.

**Р15. Поисковые синонимы** (D2): колонку в шаблон не добавляем. Общий словарь синонимов в админке (этап 4): «навара» → Navara, «гур» → насос ГПК, «приборка» → панель приладів; стартовое наполнение — из `Пошукові_запити` Prom. Работает для всех товаров, включая новые. Пер-товарный `searchKeywords` — только для импортированных с Prom.

**Р16. Импорт** (G): Prom — разовый скрипт до запуска, фото в воркере, 2–3 параллельно. Импорт таблицы — UI в админке, нужен к моменту, когда клиент начнёт вносить новые товары.

### Решения по ревью 2 (21.11.2026)

**Р17. Сайт не трогает наличие на Prom — Р1 без исключений.** KeyCRM по документации отдаёт остаток на Prom «сразу». Реальную задержку KeyCRM → Prom замерить на 5–10 товарах (вопрос клиенту 17). Исключение «сайт снимает с Prom через API» вводить, только если замер покажет минуты.

**Р18. Бронь по заказам Prom.** Воркер опрашивает заказы Prom раз в 60 с и ставит товару на сайте **бронь** (не показываем как доступный). Остаток не меняет ни в KeyCRM, ни на Prom. Решает KeyCRM: вебхук остатков подтверждает «Продано» или возвращает в наличие; нет вебхука за 30 мин — бронь снимается, значение берётся из сверки.

**Р19. Остаток — число, не флаг.** Обработчик вебхука сразу хранит доступное = `in_stock − in_reserve` в `quantity`; «Продано» при 0. Работает и для 1 шт, и для > 1, от ответа клиента не зависит. Обработчик идемпотентный, 2xx — только после записи. В теле вебхука нет ID и времени события — при сомнении в порядке сайт перечитывает оффер через API.

**Р20. Тип «Дверні карти / оббивка дверей»** в «Салоні» (Ш2). Щуп АКПП — в общем типе «Щуп масляний» (одна позиция в каталоге, отдельный тип в КПП не нужен).

**Р21. Связка с KeyCRM.** Фид отдаёт sku и как `<offer id>`, и как `vendorCode` — KeyCRM связывает публикацию Prom с существующим оффером по SKU и не создаёт дубль (справка «Creating a product from a publication»). Новый товар: сайт создаёт оффер в KeyCRM и ставит остаток через API до того, как товар уйдёт в фид. При подключении — разовая загрузка остатков (вебхук начальные не шлёт).

**Р22. Лимит API KeyCRM — проектировать под 20 запросов/мин** (в справке встречается 20 и 60), пауза ≥ 3 с, очередь в воркере.

**Р23. Сверка остатков:** каждые 30 мин — по товарам в наличии и в брони; ночью — полная. Укладывается в лимит Р22 (список остатков постранично).

**Р24. Новые товары на Prom — в течение часа.** Плановый импорт по ссылке новые товары берёт ~раз в сутки, поэтому после публикации сайт формирует дельта-фид (только новые и изменённые) и запускает импорт через Prom API `POST /products/import_url` — пачкой раз в 15–30 мин. Проверить на этапе 6: параметры, статус импорта, ограничения частоты.

**Р25. Подборы считаются на лету** (R10): альтернативы, «з цим купують», «ще з цього авто» — запросы с индексами (`partType`, `oemNormalized`, `model`, `donor`, `status`, `receivedAt`) + кэш data-layer с `revalidateTag`. Предрасчёт — только если замер страницы товара покажет проблему.

**Р26. Фото дефектов** (R4): при замене `condition` на `conditionLabel` + `conditionText` поле `condition.defects[]` переносится как `defectPhotos[]`.

### Решения по ревью 3 (внешнее, 21.11.2026)

**Шаблон и данные клиента**

**Р32. Единица продажи.** Строка = позиция продажи. Пара, которая продаётся вместе, — одна строка: расположение «комплект: ліва + права», состав — в «Комплектність», цена за комплект. «Кількість» — только для одинаковых деталей, цена за одну. Разные экземпляры (разные дефекты, фото, доноры) — разные строки и SKU, даже при одном OEM.

**Р33. Артикулы выдаются заранее.** В шаблоне в каждой строке уже стоит SKU `DLS-{лист}{0001–1000}` (Кузовні — DLS-10001…, Салон — DLS-91000). Фото: одна деталь = одна папка с именем SKU, файлы внутри — с любыми именами (как с телефона); главное — первое по имени файла; фото дефектов — необязательная подпапка «дефекти». Наклейки и переименование файлов не нужны. Строки, где заполнен только SKU, не импортируются. Если у детали уже есть уникальный SKU в KeyCRM — клиент ставит его. Импорт: «создать» и «обновить» — разные режимы, совпадение SKU при создании — ошибка.

**Р34. Стан «Б/в»** — без проверки, видимых дефектов нет. Список: Б/в, перевірений / Б/в / Б/в, з дефектами / Новий. Плашка «Перевірено» — только для «Б/в, перевірений». «Опис стану» обязателен, но может быть «Без зауважень».

**Р36. Расположение: «комплект: ліва + права» ≠ «підходить на обидві сторони».** Первое — пара в цене; второе — одна деталь, которая стоит на любую сторону. «ліва/права» в названиях Prom (11 шт.) — в очередь «Перевірити». Матрица Р10: комплект — альтернатива только комплекту; «обидві сторони» совместима с ліва и права.

**Р41. «№ авто» уникален по всей разборке** (одна машина = одна метка). Год и пробег достаточно в одной строке машины. Без № авто донор не создаётся, год и пробег сохраняются в товар.

**Р42. «Також підходить» — три колонки со списком моделей** вместо свободного текста.

**Р43. Повторный импорт:** пустая ячейка не стирает значение; очистка — явно. Форма админки, импорт таблицы клиента и импорт Prom (вместе с разметкой) проходят один и тот же валидатор; «OK» в разметке — не готовность к продаже, итог даёт валидатор. SKU и OEM в шаблоне — текстовые ячейки (не теряются нули); цена, год, пробег, количество, гарантия — с проверкой числа.

**Пилот.** Клиент сначала заполняет 15–20 разных деталей (обычная, пара, шина, двигатель, без донора, модель не из списка) — пробный импорт и замер времени, потом остальное. Оценка ревью: 5–9 мин на деталь с фото у опытного сотрудника, ~40–75 ч на 500 позиций.

**Импорт и запуск**

**Р27. Остаток старых товаров — только из KeyCRM.** Количество из xlsx и Prom для существующих товаров не записывается в KeyCRM. Начальный остаток через API ставится один раз и только для новых товаров. Покупка на сайте закрыта, пока не загружены остатки и не проверена связь с KeyCRM.

**Р29. Перенумерация дублей Prom.** Новый SKU нужен ~388 строкам. Перед изменениями — выгрузка обеих систем и таблица соответствий: promId → старый код → новый SKU → offer_id KeyCRM → основание. Неоднозначные — с владельцем. Старый код сохраняется для поиска.

**Р38. Новинки.** Первичная партия из таблицы клиента, как и Prom, — `receivedAt` пусто: детали могли лежать на складе год. Новинки — товары, добавленные после запуска. Закреп работает только для доступных товаров.

**Р40. Статусы Prom** (формат Prom): `!` — готово до відправки → в наличии; цифра (1 товар, «2») — под заказ N дней → «Перевірити»; `-` — нет в наличии, не обязательно продано → вопрос 9 клиенту.

**Остатки и Prom (проверить на этапе 6)**

**Р28. Бронь — по конкретному заказу.** Хранит канал, ID заказа, строку и количество; снимается по статусу этого заказа в KeyCRM. Нет подтверждения за 30 мин — бронь уходит менеджеру в очередь, а не снимается сама. Резерв на сайте — атомарно в БД (два покупателя не возьмут последнюю деталь).

**Р39. «Заброньовано» и «Продано» — разное.** Доступно 0 при `in_reserve` > 0 → «Заброньовано», покупка закрыта; `in_stock` = 0 → «Продано».

**Р30. Дельта-фид.** В настройках импорта Prom: товары, которых нет в файле, — не менять; фид не меняет наличие и количество (это делает только KeyCRM). Проверить на тесте до включения.

**Р31. Риск: новая карточка Prom без связи с KeyCRM.** Список публикаций KeyCRM обновляет автоматически раз в неделю, вручную — раз в сутки. До связи KeyCRM не передаёт остатки на эту карточку. На этапе 6 проверить, можно ли связывать сразу (API / ручное обновление); если нет — менеджер обновляет публикации после каждой партии, а срок «в течение часа» (Р24) обещать только после замера.

**Подборы**

**Р35. Широкие типы — альтернативы только по OEM.** Флаг `broad` в partTypes: «Помпа / термостат», «Блок циліндрів / ГБЦ», «EGR (клапан, радіатор)», «Пічка (…)», «Кондиціонер (…)», «Фільтр / корпус фільтра …», «Повітрозабірник / патрубок», «Торпедо / обшивка / накладки», «Обвіс / захист / аксесуари», «Перемикач / кнопки», «Датчик» и подобные.

**Р37. «З цим купують» — условие стороны в связи типов:** та же / противоположная / любая (фара ліва → фара права). Исключаются текущий товар, проданные, брони и составные части того же комплекта.

### Решения по моделированию подборок (21.11.2026)

Моделирование на 1407 реальных товарах сделали дважды независимо (чат-архитектор и Claude Code, `SIMULATION_RECS.md`). «З цим купують» и «широкие типы → только OEM» работают; ломаются «Альтернативи» — из-за данных клиента и слишком широких типов.

**Р44. OEM в альтернативах — только внутри того же типа и совместимого расположения.** В «Код запчастини» у клиента часто общий код или код двигателя: 88 кодов стоят на деталях разных типов (дверь, бампер и фара с одним кодом; YD25DDTi у кабины и кузова). Без правки 39% товаров с альтернативами получают нелепые (дверь к фаре); с правкой — 0, 595 товаров сохраняют альтернативы.

**Р45. «Важіль» разделён на «Важіль верхній» / «Важіль нижній» / «Важіль (інший)».** Иначе к верхнему рычагу предлагается нижний. В «З цим купують» противоположная сторона ищется в том же подтипе (верхній лівий → верхній правий).

**Р46. Кардан, Міст у зборі, Редуктор / диференціал — обязательно передня / задня.** Передний и задний — разные детали; расположение есть в названиях почти у всех.

**Р47. Импорт Prom: проверка OEM.** Код, который стоит на деталях ≥ 2 разных типов, не попадает в `oem[]` автоматически — в очередь «Перевірити» (разовый разбор ~100 кодов). `Код_товару` не считается OEM без проверки.

**Р48. Импорт Prom: модель из группы — с проверкой.** Если годы в названии не совпадают с группой (минимум 13 товаров Ranger) — «Перевірити». Для товаров из категорийных групп («Диски и резина», «Мосты,Редукторы», «АКПП/МКПП», «Двигуни», «Корневая группа» — 98 шт.) модель берётся из «Сумісність з моделлю» и названия, с проверкой.

**Р49. Шини та диски — подбор по размерам, не по модели:** альтернативы — тот же диаметр + PCD (диски) или размер (шины).

**Р50. «Ще на цю модель» (фолбэк без донора)** — сначала та же категория, затем остальное; до 8.

## 1. Принципы

1. **Клиент вводит только то, что знает он один.** Всё, что можно вычислить (категория Prom-товаров, годы, рекомендации, новинки, SEO, поисковые синонимы), сайт считает сам. Новое поле на сайте не должно превращаться в «заполните ещё 4 колонки для 500 товаров».
2. **Ключи — из списков, не из текста.** Тип детали, расположение, авто (модель), стан, пункт выдачи — выпадающие списки. Разбор названий — только подсказка для импорта Prom, не источник правды.
3. **Только детерминированные правила.** Каждое правило записано в DEV_CONTEXT §5 и покрыто unit-тестами на фикстурах из реальной выгрузки.
4. **У каждого правила — фолбэк**, и блок никогда не бывает пустым или нелепым: не набралось — блок скрыт.
5. **Любой автоматический результат виден и правится в админке.** Ручная правка важнее автоматики и не перезаписывается при пересчёте.
6. **Всё сомнительное — в очередь «Перевірити»**, не на витрину молча.

## 3. Схема: наполнение товарами и обмен остатками (на проверку)

Кто чем владеет:
- **Сайт (админка)** — контент: название, описание, фото, тип, расположение, характеристики, модель, совместимость, цена, гарантия. Товары заводятся и правятся **только здесь**.
- **KeyCRM** — остатки и заказы со всех каналов. Единственный, кто меняет наличие на Prom (Р1).
- **Prom** — канал продаж. Контент получает фидом с сайта, наличие — от KeyCRM. Руками на Prom товары не правим.
- **Ключ везде — sku** (один на физическую деталь): сайт `sku` = KeyCRM SKU оффера = Prom `Код_товару` и `<offer id>` фида (Р3, Р5). Для старых товаров дополнительно храним `promId`.

### 3.1 Наполнение

**А. Разово, до запуска**
1. Prom → KeyCRM: перенумеровать дубли кодов (212 кодов / 583 строки), чтобы sku был уникален на Prom и в KeyCRM.
2. Prom: старым товарам проставить «Ідентифікатор_товару» = sku (xlsx-импорт Prom, сопоставление по «Унікальний_ідентифікатор»). Сначала 5–10 товаров.
3. Сайт: импорт выгрузки Prom скриптом (выгрузка + разметка) → черновики → очередь «Перевірити» → публикация. `receivedAt` пусто.
4. Сайт: импорт таблицы клиента (товары, которых нет на Prom) тем же путём → черновики → публикация. `receivedAt` = дата импорта.
5. Включить фид на Prom; проверить, что Prom обновил старые товары, а не создал копии.
6. Включить вебхук остатков KeyCRM → сайт; разовая загрузка текущих остатков через API (вебхук начальные не шлёт).

**Б. Постоянно, после запуска**
```
Админка: новый товар (вручную или импорт таблицы) → публикация
   ├─▶ воркер → KeyCRM API: товар/оффер с sku, остаток = quantity        (сразу)
   └─▶ YML-фид → Prom забирает → публикация на Prom                       (новые ~раз в сутки)
                     └─▶ KeyCRM связывает публикацию Prom с оффером по sku
Правка цены/контента в админке → фид → Prom                               (цена/наличие ~раз в 4 ч)
```

### 3.2 Обмен остатками

| Событие | Что происходит | Когда сайт узнаёт |
|---|---|---|
| Заказ на сайте | сайт сразу резервирует товар у себя (не показываем как доступный) → заказ в KeyCRM через API → KeyCRM резервирует → передаёт остаток на Prom → вебхук остатков на сайт | сразу (локально), подтверждение — вебхуком |
| Заказ на Prom | опрос Prom API раз в 60 с → сайт ставит товару бронь (Р18), остаток не меняет; KeyCRM забирает заказ (~10 мин) → резерв → вебхук на сайт решает: «Продано» или снова в наличии | ≤ 1 мин (бронь), решение — вебхуком |
| Продажа офлайн / правка остатка в KeyCRM | KeyCRM → остаток на Prom + вебхук на сайт | сразу |
| Отмена заказа / возврат / оприбуткування | KeyCRM снимает резерв или добавляет остаток → Prom + вебхук | сразу |
| Расхождение (потерян вебхук, сбой опроса) | ночная полная сверка остатков через KeyCRM API | ночью |

Доступно = `in_stock − in_reserve`. Товар «Продано», когда доступно = 0 (при `quantity` > 1 — уменьшается). Если сайт пометил товар по опросу Prom, а заказ отменили — возвращает вебхук KeyCRM или ночная сверка.

**Проверить по документации и сценариям:**
- вебхук остатков KeyCRM: условия, формат, повторы при недоступности сайта;
- передача остатков KeyCRM → Prom: по какому полю связывает (sku = `Код_товару`?), как быстро;
- создание товара/оффера и установка остатка через API KeyCRM; что будет, когда KeyCRM подтянет публикацию Prom с тем же sku (связка или дубль);
- лимиты API KeyCRM (60/мин или 20/мин) и Prom API (для опроса заказов раз в 60 с);
- Prom: xlsx-импорт «Ідентифікатор_товару», сопоставление фида по `<offer id>`, интервалы обновления фида;
- гонки: два заказа на одну деталь (сайт + Prom) в окне 1–10 мин — кто выигрывает и что видит второй покупатель.

## 10. Доноры

- Донор — конкретная машина, с которой сняты детали. Ключ: **модель + «№ авто»** (метка, которой клиент различает машины).
- Год и пробег — необязательные, достаточно в одной строке; сайт подставляет всем деталям донора. Импорт: один № авто с разными моделями — ошибка; с разными годом/пробегом — предупреждение.
- Коллекция `donors` создаётся автоматически при импорте/создании товара; в админке — переименовать, объединить, разделить, добавить фото машины (одно на донора).
- Отклонено: группировка по «модель + год + пробег» без метки — опечатка делит машину на две, неизвестный пробег склеивает две машины.
- **«Ще з цього авто»**: товары того же донора в наличии, без текущего. Карточка донора — модель, год, пробег, «деталей у наявності N», фото (если есть). Фолбэк: нет донора или < 3 деталей в наличии → по модели («Ще на Ranger 2006–2012»).
- Пробег донора выводится в характеристиках двигателя/КПП.

## 11. Новинки

- Поле **дата поступления** (`receivedAt`), ставится автоматически при создании в админке и при импорте таблицы.
- Новинка = в наличии и `receivedAt` < 30 дней, или закреплена вручную. На главной — 15 самых свежих, табы по категориям.
- Товары, перенесённые с Prom при запуске, — `receivedAt` пусто → не новинки (иначе 1407 позиций станут «новыми» на месяц).
- Отличие от DEV_CONTEXT: там `isNew` от `createdAt` — заменить на `receivedAt`.

## 12. Альтернативи

Детали, которые можно купить вместо этой.
1. Тот же OEM (нормализованный) — та же деталь с другой машины.
2. Иначе: тот же тип + совместимое расположение (левая к левой; «пара» совместима с обеими) + совместимая модель (model совпадает или входит в `alsoFits`, в обе стороны).
3. Только в наличии, без текущего; сортировка: состояние (перевірений выше), затем цена. До 6.
4. Пусто → блок скрыт. Для проданного товара — главный блок страницы (с «Запитати аналог»).
5. Ручное закрепление в админке — выше автоматики.

## 13. З цим купують

Детали, которые берут в комплекте.
1. Таблица связей **типов** в справочнике (заполняется админом один раз, 30–50 строк): фара → фара другой стороны, повторювач, решітка; двигун → турбіна, ПНВТ, форсунки; важіль → важіль другої сторони…
2. Кандидаты: сначала с того же донора, затем с той же модели; только в наличии; до 3.
3. После запуска — статистика заказов: пары, купленные вместе ≥ N раз, поднимаются выше (этап 7).
4. Ручное закрепление — выше автоматики. Пусто → блок скрыт.
5. Отличие от DEV_CONTEXT: там `boughtTogether[]` и `alternatives[]` ручные — становятся ручными переопределениями поверх автоматики.

## 14. Импорт Prom (разово, до запуска)

1. Источник — xlsx-выгрузка + `DLSAuto_prom_rozmitka.xlsx`.
2. Ключ — `promId`. sku — по решению §4.
3. Название / описание: uk и ru из выгрузки. Описание: вычистить шаблонный текст и inline-стили; содержательная часть → «Опис стану» / описание.
4. Категория, тип, расположение — из разметки. «Перевірити» → очередь в админке.
5. Модель-донор — из группы Prom + «Сумісність з моделлю» по таблице соответствия «группа Prom → модель» (37 моделей листа «Моделі» → коллекция `models`).
6. OEM — из «Код запчастини», «MPN», `Код_товару` (если похож на OEM), нормализованные копии для поиска.
7. Характеристики Prom → характеристики категории, где совпадают (колір, об'єм двигуна, сторона, тип запчастини → оригінал/аналог); остальное → примечание.
8. `Пошукові_запити` ru/uk → скрытое поле `searchKeywords` (новое, участвует в поиске этапа 4).
9. Фото — скачать по ссылкам (с сервера, не из браузера), sharp-варианты.
10. Наличие: `+` → in_stock; `-` → решение клиента (sold со страницей для SEO или не переносить); `!` — уточнить.
11. Цена: `Ціна_від`, USD — в очередь «Перевірити».
12. SEO — по шаблону (тип + модель + годы).
13. `receivedAt` — пусто (не новинки).
