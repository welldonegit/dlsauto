## Что ценного и нового — берём в работу

Отсортировано по важности. Пометка: 🔴 критично к запуску · 🟠 важно · 🟢 полезно.

1. 🔴 **Вебхук остатков не содержит ни id события, ни времени — наша схема идемпотентности из DEV_CONTEXT §6 нереализуема как записана.** DEV_CONTEXT §6: «идемпотентность по event id **или** (sku, timestamp)». Но тело вебхука = `{offer_id, sku, in_stock, in_reserve}` — ни event id, ни timestamp (подтверждает и наш агент, и внешний отчёт). → Идемпотентность строить как «при неоднозначном порядке **перечитать оффер** через API», а не по event id. Правка DEV_CONTEXT §6.
2. 🔴 **Бронь нельзя привязать к заказу по вебхуку остатков.** В теле только остаток оффера — нельзя понять, *чей* заказ зарезервировал/снял. Если за 30 мин заказ Prom ещё не дошёл в KeyCRM, «положительный остаток» при сверке откроет уже заказанную деталь. → Хранить **локальную бронь по (канал, id заказа, строка, кол-во)**, снимать после сверки именно этого заказа, тайм-аут → в очередь менеджеру. Это глубже нашего sc2/sc4.
3. 🔴 **Автосинхронизация публикаций Prom в KeyCRM — раз в неделю** (ручное массовое — раз в сутки; заказы — раз в 10 мин). → Наш sc5 («новый товар не связан») серьёзнее: без ручного триггера связь публикации может не появиться **до недели**. Обещание «товар на Prom завтра» (Р5) относится к фиду, а **связка для обмена остатком** — отдельный и более медленный шаг. Подтвердить по [k-faq], заложить ручной триггер связи.
4. 🟠 **11 строк разметки используют расположения, которых нет в списке шаблона** («пара/обидві», «задня пара/обидві», «передня пара/обидві»; в шаблоне — «пара (ліва + права)»). → Разметка и клиентский список говорят на разном словаре позиций. Импортёр либо отвергнет эти 11, либо нужно единое перечисление (и в `lst_pos`, и в разметке, и в матрице осей Р10). Мы это **пропустили** в обеих итерациях.
5. 🟠 **«OK» ≠ готово к продаже; валидатор разметки должен быть тем же, что примет таблицу клиента.** Прогнать все 1407 строк тем валидатором, что будет у импорта (а не отдельной разметкой). Новые исключения показать отдельно от текущих 53. Процессно сильнее нашего «очередь Перевірити».
6. 🟠 **Дельта-фид и «пропущенные в файле» товары.** Prom умеет действия над позициями, которых нет в файле; из дельты исключён почти весь каталог. Нужно явно задать режим «сохранять пропущенные» и список обновляемых полей, иначе контентный фид может задеть наличие/количество. Проверить на изменённой-отсутствующей-проданной карточке до включения в бою. (Мы фид-матчинг проверяли, но не поведение «missing items».)
7. 🟠 **Нет состояния «Б/в, не перевірявся».** `lst_stan` = перевірений / з дефектами / Новий. Непроверенную б/у деталь некуда отнести (вынудит выбрать «перевірений»). Плюс «Перевірено» на витрине берётся из состояния (Р14) — ложно-положительное. → Добавить нейтральное состояние. Проверено по файлу — список именно 3 значения.
8. 🟢 **388 строкам нужен новый SKU** (583 − 212 + 17). Конкретный объём перенумерации (Р3/Р5) — у нас был только качественно. Пять капотов с одним OEM по OEM не разнести — только ручной разбор экземпляров.
9. 🟢 **`relatedTypes[]` не выражает «та же ось, противоположная сторона»** (фара → фара *другой* стороны). Тип→тип-связь предложит левую фару к левой или сам текущий SKU. → В «З цим купують» хранить условие связи (ось/сторона), исключать текущий/проданный/бронь. Уточняет наш R6 для boughtTogether.
10. 🟢 **В шаблоне нет числовой валидации** (цена, гарантия, кол-во, год, пробег — без проверки; `allowBlank=true`, `showErrorMessage=false`). Импортёр обязан валидировать сам, в т.ч. вставленные значения. Диапазоны C/D/E…: строки 2–1001.
11. 🟢 **Диаметр R14–R20 в Excel vs R15–R20 в справочнике; «так» безусловное.** Подтверждено: `lst` = R14…R20, справочник пишет «список: R15 … R20» и «так». Свести словарь и обязательность (по §8 — только для дисков).
12. 🟢 **Оценка трудозатрат клиента: ~500 деталей ≈ 42–133 ч с фото** (2–9 мин/деталь ввода без поиска применимости/диагностики). Полезно для планирования пилота (15–20 деталей) и ожиданий владельца. У нас такой оценки не было.
13. 🟢 **Косая черта в коде → путь файла** (1 строка). Выданный «безопасный» SKU снимает проблему именования фото.

## Что спорно / требует осторожности

- 🟠 **Связка по SKU без дубля — отчёт осторожнее нас.** Мы (по агенту) написали «KeyCRM линкует по SKU, дубля нет». Отчёт: подтверждено **только для операции «создать товар из загруженной публикации»**; автоматическую связь *любой новой карточки фида без доп. действия* — «не нашёл». С учётом недельной автосинхронизации (п.3) это ближе к истине. → Смягчить наш вывод sc5: «снято для документированного потока create-from-publication; авто-связка по времени/триггеру — проверить в кабинете».
- 🟠 **«Старым карточкам сменить внешний ID на SKU» — отчёт: «не нашёл гарантии ни для одного варианта».** Наш агент считал это подтверждённым (с нюансом). Разночтение → проверить на 5–10 товарах до массовой перенумерации (Р5 и так это предписывает).
- 🟡 **«105 типов / 1354 / 53»** — против наших файлов (104/1334/73). Не ошибка отчёта, а другой (v3) набор файлов. Сверить после получения v3.
- 🟡 **Декодинг `!`/`2`** — правдоподобен и соответствует семантике Prom, но наш собственный doc-check это отдельно не подтверждал. Пометить «подтвердить в кабинете».
- Ряд пунктов отчёта ссылается на Р17–Р26 и §3.1/§3.2, которых **у нас нет** — оценить их можно только по v3.

## Чего в отчёте нет, а у нас есть (не потерять при сведении)

4. В шаблон: добавить состояние **«Б/в, не перевірявся»**; свести диаметр R14 vs R15–R20.
