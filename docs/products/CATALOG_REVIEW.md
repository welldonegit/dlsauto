## B. Ошибки в плане (что / почему / как исправить)

**B1. §2: «Код_товару = OEM в 1086 случаях» — занижено.**
Пересчёт: точных совпадений `Код_товару` = характеристика «Код запчастини» — **1205**, с нормализацией (убрать пробелы/дефисы/регистр) — **1211** (из 1312 строк, где заполнены оба). Качественный вывод плана («артикул ≈ OEM») верен и даже сильнее, но число нужно поправить на 1205/1211, иначе §4 опирается на неточную цифру.
*Исправить:* заменить в §2 «1086» → «1205 (1211 после нормализации)».

**B2. §7: 11 из 73 «Перевірити» — на типах со стороной «бажано», а план утверждает «почти все — там, где сторона обязательна».**
По справочнику: `Скло` и `Важіль` — сторона **«бажано»** (не обязательна). Но 3 «Скло» и 8 «Важіль» попали в «Перевірити» с причиной «немає сторони». То есть логика разметки флагует «немає сторони» и для «бажано»-типов — это противоречит и справочнику (бажано ≠ блокер), и фразе §7.
*Почему важно:* клиент получит ~11 ложных «Перевірити», где править нечего («Важіль Toyota Hilux», «Скло кунга» — стороны либо нет, либо она не нужна).
*Исправить:* в логике разметки флаговать «немає сторони» только для `обов'язково`-типов; для `бажано` — статус OK. Отдельно: `Важіль` — тип-свалка (рычаг подвески / ручка ручника / рычаг кулисы), часть этих строк стоит пере-типизировать вручную, но не по причине «немає сторони».

**B3. §7: 5 «Подушка безпеки» со статусом OK имеют сторону в названии, но пустое «Розташування» — баг извлечения стороны.**
Строки «Подушка безпеки **водійська**…», «…**пасажирська**…» (правило — `водійська / пасажирська`, обязательное) помечены **OK** и при этом «Розташування» **пусто** — сторона из названия не извлеклась. В то же время подушки **без** стороны корректно ушли в «Перевірити». То есть парсер не распознаёт `водійська/пасажирська` как значение стороны: часть теряет данные молча (OK + пусто), часть флагует. Несогласованно.
*Исправить:* добавить `водійська/пасажирська` (и синонимы «водительская/пассажирская», «пасажир») в извлечение стороны для `seat`-типов; эти 5 строк должны получить заполненное «Розташування», а не OK-с-пустым.

**B4. §7: «Дверні карти» типизированы как «Двері»; «ляда/двері багажника» флагуются «немає сторони», хотя стороны у них нет.**
- 3 строки «Дверні карти / Комплект дверних карт» (обшивка двери — элемент салона) отнесены к типу `Двері`. Это разные вещи: дверная карта ≠ дверь.
- Несколько «Двері багажника / багажна ляда» (Jeep Patriot, Kia Sorento, Toyota RAV4, Hyundai Terracan, VW Caddy) флагуются «немає сторони», но у задней двери/ляды левой/правой стороны нет. Тип `Двері` смешивает боковые двери (сторона `lr`) и ляду (стороны нет).
*Исправить:* (1) для «дверних карт» завести/использовать тип обшивки салона (`Торпедо / обшивка / накладки` или новый «Оббивка дверей»), перенести из «Кузовні» в «Салон»; (2) ляду/заднюю дверь багажника относить к существующему типу `Борт / кришка багажника` (сторона — `—`), а не к `Двері`. Обе правки снимают часть ложных «Перевірити».

**B5. §7: 2 ошибки типа в выборке 100 OK (подтверждают «1–2», но конкретику стоит пофиксить словарём).**
- «**Радіатор егр** SsangYong Rexton» → отнесён к `Радіатор охолодження`, хотя есть отдельный тип `EGR (клапан, радіатор)`.
- «**Щуп акпп** Jeep Grand Cherokee» → отнесён к `АКПП` (по слову «акпп»), хотя это масляный щуп, а не коробка.
*Исправить:* в словаре приоритезировать более длинные/специфичные маркеры («радіатор егр», «щуп») выше родовых («радіатор», «акпп»). Это разовая правка перед импортом, на витрину эти 2 не должны попасть как АКПП/радиатор охлаждения.

**B6. §3/§6 (критично для архитектуры): у KeyCRM НЕТ вебхука изменения остатков — схема «остатки на сайт через вебхук KeyCRM» нереализуема как описано.**
Официальная документация KeyCRM перечисляет вебхуки `order.change_order_status`, `order.change_payment_status`, `lead.change_lead_status`. **Отдельного stock/остатки-события нет.** И в DEV_CONTEXT §6 («KeyCRM шлёт вебхук изменения остатков `/api/webhooks/keycrm/stock`»), и в диаграмме §3 плана этот канал предполагается — он не поддерживается.
*Исправить:* остатки с KeyCRM забирать **поллингом** API офферов/остатков (по `sku`/`offer_id`, лимит 20 запросов/мин) по расписанию в воркере, либо пересчитывать по событию `order.change_order_status`. Поправить DEV_CONTEXT §6 (см. §G).

**B7. §3: Prom сопоставляет товары фида по своему UUID, а не по артикулу — риск дублей, если не хранить UUID.**
Prom матчит позицию фида по `<offer id>` (в Excel — колонка «Ідентифікатор_товару», куда кладут «Унікальний_ідентифікатор» Prom). Это **UUID Prom, не ваш `sku`**. Если фид не вернёт известный Prom UUID — Prom заведёт **новый** товар. Открытый вопрос §3 «по какому полю Prom сопоставляет» — закрыт: по UUID.
*Исправить:* при первичном импорте сохранить присвоенные Prom UUID у себя (`promId` уже есть в модели) и отдавать их в фид `<offer id>`; иначе каждое обновление плодит дубли (а артикулы на Prom и так не уникальны — §2).

**B8. §3/§6: гонка за «наличие на Prom» — его ставят двое.**
План: наличие на Prom меняет (а) сайт напрямую через Prom API при продаже и (б) KeyCRM, отдавая остатки в Prom (штатно). Два писателя в одно поле → возможны «качели»/перетирание.
*Исправить:* выбрать **один источник правды** для остатка на Prom. Рекомендация — KeyCRM (он видит заказы и резерв со всех каналов), тогда сайт не трогает Prom API по наличию; либо сайт — тогда отключить отдачу остатков KeyCRM→Prom. Зафиксировать выбор в DEV_CONTEXT §6.

**B9. §9/§4 (Part 4): «список моделей из сида» недостаточен — сид содержит только 16 моделей / 8 марок, а каталог охватывает 17 марок / 31 группу Prom.**
Сид (`scripts/seed.ts`) — демо-набор дизайна: 16 моделей, бренды только Mitsubishi, Ford, Mazda, Nissan, Jeep, Toyota, Isuzu, Hyundai, Kia. В выгрузке же есть VW (Touareg, T5, Crafter, Caddy), Mercedes ML W163, BMW X5 E53, SsangYong (Rexton, Actyon), Volvo XC90, Peugeot/Fiat Titano и др. Список брендов шаблона — **17** (добавлен Great Wall), сид — **16**. Собрать дропдаун «Модель / покоління» из текущего сида = оставить без модели бо́льшую часть реальных товаров.
*Исправить:* дропдаун моделей и марок генерировать из **реальной коллекции** `models`/`brands` на момент скачивания шаблона (это уже заложено в §9 «списки генерируются из актуальных…»), а коллекцию `models` перед наполнением расширить до реальных 26+ поколений, покрыв все 17 марок и 31 группу соответствия Prom. Статический v2-файл — только временная заглушка. См. §K — список из сида и как подставить.

- **D2 — поисковые синонимы у новых товаров**: §9 относит «поисковые синонимы» к «считается автоматически», но автоген заложен только для импорта Prom (`Пошукові_запити` → `searchKeywords`). Для товаров, которые клиент вносит таблицей, синонимов не будет (поиск только по `name`/`description`). Либо добавить необязательную колонку «Пошукові слова» в шаблон, либо честно записать, что для новых товаров синонимов нет, а §9-формулировку «автоматически» сузить до импорта.

### Неиспользуемые колонки шаблона
Явно лишних колонок не найдено — все (A–U + характеристики) ложатся в поля §15. Пограничные:
- «Гарантія, днів» (S) — используется только если гарантия зависит от товара (вопрос владельцу 7); если гарантия общая по категории — колонка почти всегда пуста (не ошибка, но стоит убрать, если ответ «одна на всё»).
- «Комплектність» (T) — ляжет в `completeness`; редко заполняется, но безвредна.

## D. Риски

**R1. `specs[]` (этап 3b) vs характеристики категории (§8) — не состыкованы.**
В модели уже есть свободный `specs[]` (label/value), и `ProductCard` рендерит `specs.slice(0,4)`. §8 вводит шаблон характеристик на категорию (структурированные поля). Не описано, как они сосуществуют: шаблонные характеристики пишутся **в** `specs[]` (вычисляемо) или живут отдельными полями, а `specs[]` остаётся ручным «хвостом»? Без решения получится две параллельные панели характеристик.
*Рекомендация:* характеристики категории — отдельные типизированные поля (из `specTemplate`), а в панель карточки/quick-view собирается вычисляемый список `Стан → хар-ки категории → Пробіг → Авто-донор`; свободный `specs[]` оставить как ручной оверфлоу-хвост или убрать. Решить до миграции.

**R2. `model` сейчас играет роль донора; план разделяет `model` (совместимость) и `donor` (конкретная машина).**
В текущей `Products` поле `model` подписано «Модель (донор)», и `fromSameCar` задуман по `model`. План §10 вводит `donors` (модель + «№ авто»), а `model` оставляет под совместимость. Это смена семантики существующего поля → миграция данных сида/импорта и переписывание `fromSameCar` (сейчас не реализован — в `productCard.ts` заглушка).
*Рекомендация:* `model` = поколение (для «підходить на ваше авто» и метки), новый `donor` = машина; `fromSameCar`/«Ще з цього авто» перевести на `donor` с фолбэком на `model`.

**R3. Дублирование `category` и `partType`.**
§15 добавляет `partType` (обяз., rel → `partTypes`, у которого есть `category`), но **оставляет** `category` отдельным обязательным полем. Два источника категории → дрейф (товар с типом из одной категории и вручную выставленной другой `category`).
*Рекомендация:* `category` выводить из `partType.category` (read-only/вычисляемо) либо проставлять хуком при выборе типа; не давать редактировать независимо.

**R4. Миграция `condition` (группа `{text, defects[]}`) → `conditionLabel` + `conditionText`.**
§15 заменяет `condition` на `conditionLabel` (enum) + `conditionText`. Текущая группа содержит ещё `defects[]` (фото дефектов). При миграции нельзя потерять `defects[]`.
*Рекомендация:* `condition.text` → `conditionText`; добавить `conditionLabel`; `condition.defects[]` сохранить (отдельное поле `defectPhotos[]` или оставить в составе фото). Явно прописать в §15.

**R5. `isNew` от `createdAt` → `receivedAt`.**
`src/lib/rules/isNew.ts` считает по `createdAt` (+ `pinnedNew`), есть тест. §11 переводит на `receivedAt`. Нужно: поле `receivedAt`, правка `isNew` и его вызовов, правка теста, и чтобы импорт Prom ставил `receivedAt` пустым (иначе 1407 позиций станут «новыми»). Небольшая, но реальная миграция + изменение бизнес-правила DEV_CONTEXT §5.

**R6. Матрица совместимости «Розташування» для альтернатив не определена.**
§12 говорит «ліва к ліва; пара совместима с обеими», но не покрыты пары вроде «ліва» ↔ «передня ліва» ↔ «передня». Деталь с «ліва» (без оси) и деталь с «передня ліва» — альтернативы или нет? Без явной матрицы алгоритм даст либо лишние, либо пропущенные альтернативы.
*Рекомендация:* задать матрицу совместимости позиций явной таблицей (напр.: «передня ліва» ⊂ совместимо с «ліва» и «передня»; «пара» ⊇ всё) и покрыть unit-тестами.

**R7. Twin-модели (Navara/Pathfinder): путь выбора и матчинга неясен.**
В сиде Pathfinder — не отдельная модель, а `twinName` у Navara R51. Значит в селекторе «Оберіть авто» Pathfinder не выбрать. При этом §5 «підходить на ваше авто» = model совпадает **или входит в alsoFits** — близнец автоматически **не** включён. Покупатель-владелец Pathfinder не увидит деталей Navara, если не завести отдельную модель Pathfinder или не прописать её в `alsoFits`.
*Рекомендация:* решить одно из двух — (а) близнец = отдельная выбираемая модель, у деталей обе модели в `alsoFits`; (б) матчинг «на ваше авто» учитывает `twinName`. Сейчас — дыра в сценарии twin.

**R8. Нумерация доноров зависит от дисциплины клиента (§10).**
Ключ донора = «модель + № авто». Если клиент не метит машины (вопрос 6), все детали модели склеятся в один «донор», и «Ще з цього авто» выродится в «Ще на модель». Не блокер (есть фолбэк), но ценность блока падает.

**R9. Импорт 1407 товаров: 135 «немає», 52 «!», 33 без фото, 318 кол-во>1, 74 «Ціна_від», 1 USD, 2 «пара», 21 «комплект».** Все эти хвосты требуют решения до импорта (вопросы клиенту 2,4,5 + §11 п.10–11). Не риск кода, а риск «импортнули мусор на витрину».

**R10. Вычислять на лету vs предрасчитывать (1500–5000 товаров).**
Для такого объёма Postgres — «на лету» достаточно: альтернативы (match по `oemNormalized`, затем `partType`+`position`+`model`), «з цим купують», «Ще з цього авто» — индексируемые запросы на странице товара; каталог и «Нові надходження» их не трогают. **Рекомендация: считать на лету** с индексами (`partType`, `oemNormalized`, `model`, `donor`, `status`, `receivedAt`) и кэшировать в data-layer (`unstable_cache` + `revalidateTag` на `afterChange`). Предрасчёт вводить только если замер p95 страницы товара покажет проблему. 5000 строк для Postgres — малый объём; предрасчёт сейчас — преждевременная оптимизация.

2. После первого импорта забрать присвоенные Prom UUID и хранить в `promId`, отдавать в `<offer id>` — иначе дубли.
3. Заказы: Prom → KeyCRM (нативно, ~10 мин) → вебхук `order.change_order_status` → сайт.
4. Остатки — **один источник правды**. Вариант A (рекомендуется): KeyCRM ведёт остаток и отдаёт в Prom; сайт получает остаток **поллингом** KeyCRM API (по `sku`/`offer_id`). Вариант B: сайт ведёт остаток, при продаже сам ставит `presence` в Prom API и обновляет фид; отдачу KeyCRM→Prom отключить.
5. Не полагаться на несуществующий stock-вебхук KeyCRM — только поллинг API или событие статуса заказа.

## G. Импорт таблицы в админке §9 — объём, этап, риски

- **Объём разового импорта Prom:** 1407 товаров, 1–10 фото (33 без фото), фото тянуть **с сервера** по `images.prom.ua`. Ориентир — 5–8 тыс. изображений, sharp-варианты (thumb/card/gallery WebP) → ощутимая нагрузка на VPS-3 (2 CPU / 6 GB).
- **Этап:** импорт Prom — разовый, до запуска (§14). Админский импорт таблицы клиента (§9) — отдельный инструмент, нужен к моменту, когда клиент начинает вносить **новые** товары (после запуска). Не смешивать: Prom-импорт — скрипт, таблица — UI в админке.
- **Cloudflare Free — 100 MB на запрос:** архив фото грузить частями (в плане учтено). Нужен чанк-аплоуд + сборка на сервере.
- **Обработка фото на VPS-3:** sharp по тысячам файлов — только в воркере, с ограничением конкуренции (2–3 параллельно), очередь + прогресс; иначе OOM/таймаут. Не в запросе-обработчике импорта.
- **Повторный импорт:** «тот же артикул = обновление, не дубль» — работает только при уникальном `sku` (ровно то, ради чего §4). Для Prom-импорта ключ — `promId` (B7); для таблицы — `sku`/«Артикул». Нужна явная проверка уникальности артикула **внутри** загружаемого файла до создания (в §9 отчёт это есть: «артикул повторюється»).
- **Риск размера:** 318 товаров кол-во>1 и «комплект/пара» — если клиент ответит, что кол-во реально, в архиве и в отчёте это не меняет объём, но меняет модель (`quantity`).
