## А. Модель данных и сид

1. **Миграция** коллекций под DEV_CONTEXT §4 v1.3: `products` (partType, position, donor, receivedAt, quantity, conditionLabel + conditionText + defectPhotos[], warrantyDays, isOriginal, completeness, specValues[] + specs[] как «Додатково», searchKeywords, category — вычисляется из partType и в админке только для чтения), новые коллекции `partTypes` и `donors`, `categories.specTemplate[]`. Данные `condition.defects[]` при миграции не терять (Р26).
2. **Справочники в сид — из документов, не выдумывать:**
   - 9 категорий — CATALOG_PLAN §6, со `specTemplate` по листу «Характеристики» справочника;
   - 107 типов — справочник: категория, правило расположения (`lr` / `fb` / `any` / `seat` / `none`), флаг `broad` (Р35), связи типов с условием стороны — стартовая таблица `SIMULATION_RECS.md` §2 с поправкой Р45;
   - 37 моделей — лист «Моделі»: марка, модель, поколение, годы, bodyType. Twin-модели — отдельные записи (Р11), совместимость через alsoFits.
   - Марки — те, что есть в моделях.
3. **Товары для сида — 20–30 живых товаров из выгрузки Prom**, а не выдуманные.
   - Выгрузка в `.gitignore`, поэтому сид её не читает. Разовый скрипт (в репозиторий не коммитить) выбирает товары и сохраняет образец в репозиторий: `scripts/seed/fixtures/prom-sample.json` + фото в `scripts/seed/fixtures/photos/` (по 2–4 на товар, скачать с images.prom.ua, через Git LFS как остальные картинки). Сид читает только образец.
   - Брать только товары в наличии со статусом OK в `DLSAuto_prom_rozmitka.xlsx`; категория, тип, расположение — из разметки. Модель — по группе Prom → модель из листа «Моделі» (только однозначные группы, без категорийных).
   - Набор подобрать так, чтобы правила подбора было видно в работе: 2–3 модели с несколькими деталями каждая (например, Ranger 2006–2012, Navara D40, Pajero Sport I); фары левая + правая одной модели; рычаги верхний и нижний; двери передние / задние, левые / правые; двигатель + турбина + ПНВТ + форсунки одной модели; деталь широкого типа с одинаковым OEM на двух моделях (например, помпа Pajero Sport / L200); 2–3 диска или шины.
   - Очистить при переносе: артикулы — свои `DLS-…` (не `Код_товару`); OEM — только реальный номер этой детали (коды, стоящие на деталях разных типов, и коды двигателей у кузовщины — убрать, Р44 / Р47); описание — без HTML и шаблонного текста Prom; названия и описания uk + ru из выгрузки.
   - Недостающее в данных Prom проставить в образце явно и пометить в JSON (`"demo": true` у поля): донор «№ авто» на 4+ детали одной модели; один товар «Продано», один «Заброньовано»; quantity 3 у одного; скидка и featured у двух; гарантия (14, у одного 0); стан — все три варианта; закреп в новинках; «комплект: ліва + права» и «підходить на обидві сторони» — по одному (можно из пары фар / подходящей детали); фото дефекта — у одного.
   - Список выбранных товаров (Prom ID → артикул → что демонстрирует) — в отчёт.
4. **Главная не должна поехать.** После пересида пройти главную на 390 / 1280 / 1536 / 1920: блоки категорий (новые 9 названий, фото — заглушки до реальных), «Деталі для вашого авто» (twin-модели теперь двумя карточками — это ожидаемо), новинки, пікапи / позашляховики. Если блок главной ломается из-за новой модели — исправить в рамках этапа, вид блока не менять.
5. Новое поле — правка DEV_CONTEXT §4 в том же коммите. Генерация типов — `pnpm generate:types`.

## Б. Страницы

Страницы — по экспорту: каталог, категория, марка, модель, товар, «Обране», «Порівняння» (и всё, что экспорт относит к ним: фильтры, сортировка, пагинация / «Показати ще», пустые состояния, хлебные крошки, мобильные варианты). URL — DEV_CONTEXT §8; если для нужного вида страницы URL в §8 нет — вопрос с дефолтом, не выдумывать молча.

**Сначала — карта:** в `docs/stages/stage3c/manifest.md` таблица «страница / URL / файлы экспорта / состояния». Потом по каждой странице — манифест из экспорта (элементы, количество, пропорции, шрифты, цвета, поведение) → вёрстка → сверка → коммит.

**Поведение, которого нет на канвасе, — из документов:**
- Состояния товара: в наличии (с количеством), «Заброньовано», «Продано» (Р39). У проданного страница остаётся (200), покупка закрыта, на первом плане альтернативы.
- Плашки под OEM (Р14): наличие + количество; «Гарантія N днів» — из `warrantyDays`, при 0 не показывается; «Перевірено» — только при стане «Б/в, перевірений».
- Подборы (DEV_CONTEXT §5, считаются на лету с кэшем, Р25): «Альтернативи» (Р10, Р35, Р36, Р44, Р49); «З цим купують» (Р37, Р45); «Ще з цього авто» — по донору, фолбэк «Ще на цю модель» с сортировкой Р50; «Підходить на ваше авто» — по model и alsoFits. Ручные закрепления — первыми. Проданные и забронированные в подборы не попадают; пусто — блок скрыт.
- Новинки — по `receivedAt` (Р9, Р38).
- «Обране» и «Порівняння» — переживают перезагрузку, счётчики в шапке.
- Кэш: хуки afterChange / afterDelete коллекций → `revalidateTag` (задача из «Dev / verify» 3b).

**SEO и аналитика страниц:** title / description (шаблоны из Payload, не из кода), canonical, hreflang uk / ru / x-default; JSON-LD BreadcrumbList на всех, Product (цена, наличие) на товаре. dataLayer: `view_item_list` (листинги), `select_item`, `view_item` (товар), `add_to_wishlist`, `add_to_compare`.

## Правила (без изменений)
- Экспорт — источник правды по составу и виду. Ничего не додумывать; конфликт экспорта и документов — вопрос владельцу.
- Ширина страницы — только `<Container>` (1376); горизонтальные ленты — общий `.dls-rail`. Сверка всегда на 390 / 1280 / 1536 / 1920.
- Токены вместо px / hex; редакционные тексты — в Payload; новое поле — DEV_CONTEXT §4 в том же коммите.
- Утверждённые страницы (главная, 3a) не менять, кроме вынужденного новой моделью — с отдельной сверкой.

## Приёмка
1. Миграция и сид прогоняются с нуля без ручных шагов; в админке товар заводится с новыми полями, категория подставляется из типа.
2. Каждая страница: манифест → сверка 390 / 1280 / 1536 / 1920 рядом с экспортом, два списка расхождений пустые; 0 console-errors; uk / ru.
3. Unit-тесты правил подбора и состояний: матрица расположения, broad → только OEM, OEM в пределах типа, пары и комплекты, сторона в «З цим купують», фолбэк донора, receivedAt, «Заброньовано» / «Продано».
4. Главная после пересида — сверка пройдена.
5. Проверки зелёные: typecheck, lint, check:literals, check:container, tokens:check, тесты; прод-сборка собирается.
6. Отчёт `docs/stages/STAGE_3C_REPORT.md`: прогресс по коммитам, решения по умолчанию, отложенное, что проверить владельцу руками (по страницам, коротко). ROADMAP — статус 3c.

Коммиты — Conventional Commits, отдельный на миграцию, сид, каждую страницу.

**Пункты:**

   reserved/sold не купить нигде, в листингах/подборах/счётчиках их нет; на товаре/Обраному/

Короткая сессия по итогам отчёта «Доводка перед приёмкой (27.11)». Новых страниц, блоков и
полей нет. Правила прежние: свой коммит на пункт, сверка на 390 / 1280 / 1536 / 1920, одна

**Решения владельца:** «На ваше авто» при 0 деталей — вкладка скрывается; нейтральная

**Пункты:**
1. Миграции штатной командой. Найти причину зависания `payload migrate` и устранить её (ручное

3. Футер: рабочие ссылки. Колонка марок → страницы марок из `brands`; «Покупцям»/«Компанія» → на
