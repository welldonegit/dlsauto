# Етап 2 — звіт

Модель даних, адмінка на українській, шар даних, бізнес-правила, seed, імпорт з Prom. БД піднімається тільки через `docker compose up -d`; міграції закомічені; `pnpm db:seed` відпрацьовує на чистій БД.

## Зроблено

- **Бізнес-правила** (`src/lib/rules`, unit-тести): транслітерація slug uk→latin, нормалізація OEM, українські форми «деталь/деталі/деталей», `isNew` (30 днів / `pinnedNew`), дата відправки «Сьогодні/Завтра/У понеділок» (Europe/Kyiv, поріг 15:00). Статус «Зараз відкрито» — `src/lib/hours` (з етапу 1) + `src/lib/schedule` (форматування графіка, «графік уточнюється» для непідтверджених).
- **Колекції Payload** (`src/payload/collections`) строго за DEV_CONTEXT §4: brands, models, categories, products, pickup-points, orders, leads, reviews, banners, media, pages, users; глобал settings. Локалізація uk/ru за списком §4; слаги спільні. Рольовий доступ (`src/payload/access`): admin — усе; manager — товари, замовлення (читання), заявки, відгуки, банери; settings і users — лише admin. Публічне читання — тільки опубліковане/не-hidden.
- **Products**: `sku` унікальний/обовʼязковий; `oem[]` + прихована нормалізована копія `oemNormalized` (хук); перехід у `sold` проставляє `soldAt`; валідація ціни > 0; прапори featured/pinnedNew/seasonalDecor; звʼязки alsoFits/boughtTogether/alternatives; `needsTranslation` для імпорту.
- **Media**: sharp-варіанти thumb 400 / card 800 / gallery 1600 (WebP) + оригінал, focal point, обовʼязковий локалізований `alt`; приймає зображення та mp4. Файли — `./data/media` локально (gitignore), `/data/media` на сервері.
- **Pages**: `layout` з 20 типами блоків (`src/payload/blocks`) за PROJECT_CONTEXT §4–5, з українськими лейблами; блоки автонаповнення (новинки/пікапи/позашляховики) мають «ліміт» і «закріпити вручну». Фронтенд-рендер блоків — наступний етап (каркас не чіпали).
- **Settings** (глобал): телефони, email, месенджери, соцмережі, рейтинг Prom, маркетплейси, мін. замовлення, час відправки, умови передоплати, «Приймаємо», ФОП, сезон, KeyCRM base URL.
- **Шар даних** (`src/lib/data`): типізовані `getSettings/getPickupPoints/getBrands/getModelsByBrand/getCategoryTree/getProduct/getProductsByModel/getPage` поверх Local API з `unstable_cache` + теги; інвалідація хуками `afterChange/afterDelete` (ADR 006). `partsCount` рахується в шарі, не зберігається.
- **Seed** (`pnpm db:seed`, ідемпотентний): 16 марок з логотипами з експорту (моно + кольорові де є), 16 моделей з роками/близнюками, 9 категорій (назви й лічильники — з експорту), 2 пункти видачі, settings, сторінки Головна/Про компанію/Контакти/Оферта/Політика/404 блоками, 39 товарів з фото-заглушками, 3 відгуки.
- **Імпорт з Prom** (`pnpm import:prom [file.yml]`): парсинг стандартного `yml_catalog` (`fast-xml-parser`), маппінг категорій (`scripts/prom-category-map.json`), товари → `hidden` з `needsTranslation`, фото завантажуються в media, `promId`/`sku` збережені; ідемпотентно по `promId`. Фікстура — `scripts/fixtures/prom-sample.yml` (10 offers).
- **Адмінка**: українські лейбли/назви колекцій, групи в сайдбарі (Каталог / Контент / Замовлення / Система); у товарах — колонки sku/назва/категорія/модель/ціна/статус/пункт, пошук по sku/назві/OEM; масові дії — вбудований bulk-edit Payload (статус, seasonalDecor, featured, пункт); дашборд-лічильники (в наявності / продано за 30 днів / заявки).
- **Контакти, хедер, футер — на даних з адмінки**: телефон, графік, месенджери, адреси, живий статус тепер із settings/pickup-points. Верстка не змінена (SiteHeader-обгортка годує клієнтський Header; Footer — async серверний).

## Сверка (Playwright, Контакти, проти етапу 1)

Знімок `/contacts` зібраного застосунку проти бейслайнів етапу 1 (`docs/stages/stage1/compare/built-*.png`):

- **1280 — 0.065% різниці**, дві тонкі смуги: рядок живого статусу (залежить від часу доби) і один рядок адреси у футері. Структурних зсувів немає.
- **390 — +20px висоти**: єдина змістовна зміна — адреса Запоріжжя тепер з одного джерела в адмінці (в етапі 1 картка «Контактів» і футер показували **різні** плейсхолдери); довший текст переноситься на мобайлі й зсуває футер нижче. Це наслідок уніфікації джерела, не регресія верстки.

Висновок: **регресій верстки — 0**; відмінності — лише живий статус (час) і уніфікована адреса з адмінки.

## Рішення та відхилення

- **ADR 006** — шар даних: Local API + `unstable_cache` + ревалідація хуками. Next 16 змінив `revalidateTag(tag, profile)` → передаємо `'max'`.
- **ADR 007** — без PostGIS: `mapCoords` групою `{lat,lng}` (тип `point` вимагає PostGIS, якого немає в образі); порядок — через Payload `orderable`, а не окремий `sortOrder`.
- **Імпорт**: `name` обовʼязкове й локалізоване, тож російський текст Prom кладемо в uk-поле як плейсхолдер і ставимо `needsTranslation` (буквально порожнє uk неможливе при required). Машинний переклад — пізніше.
- **Фото логотипів** — SVG через sharp (растеризуються у WebP-варіанти); кольорові лого є для 10 з 16 марок (решта — лише моно, як в експорті).

## Не зроблено і чому

- **Дані Дніпра** (адреса, графік) — плейсхолдери, графік «уточнюється» (PROJECT_CONTEXT §1, чекає клієнта).
- **Жива карта, i18n ru-контент, мега-меню, пошук** — наступні етапи (в seed ru-поля порожні, працює fallback на uk).
- **Рендер блоків сторінок** — за ТЗ лише модель; верстка блоків — етап 3.
- **Масові дії окремими кнопками** (напр. «позначити святковою») — покриті вбудованим bulk-edit Payload; окремі кастомні кнопки не додавали.

## Що перевірити руками

1. `docker compose up -d` → `pnpm db:migrate` → `pnpm db:seed` на чистій БД (або `docker compose down -v` спершу).
2. `/admin` (admin@example.com): завести марку → модель → категорію → товар з фото; перетягнути порядок; виділити 5 товарів → Edit → змінити статус/пункт.
3. Дашборд адмінки — три лічильники.
4. `/contacts` на 1280 і 390: телефон/графік/адреси/статус з адмінки; Дніпро — «графік уточнюється».
5. `pnpm import:prom` → у товарах 10 позицій `hidden` з позначкою перекладу і фото; повторний запуск не дублює.
6. `pnpm test` (23 зелені), `pnpm typecheck`, `pnpm lint` — чисто.

> Примітка dev-кеш: після зовнішнього `db:seed` перезапускати дев через `pnpm devsafe` (інвалідація `unstable_cache` — ADR 006).
