### Пункт 4 — вкладка «На ваше авто»: как читаются данные

Клиент `ProductRecommend` (cookie `dls_car` = `{slug,label}`) → `fetch('/api/favorites?
skus=<текущий>&car=<modelSlug>')` → route handler → `favoritesData` → **`getProductsByModel`**
(data-layer, ADR 006). Прямых обращений к Payload из клиента нет. `getProductsByModel`
обёрнут в `unstable_cache` с ключом, включающим **аргумент модели** (разные модели → разные
записи кэша) и тегом `products` — персональный результат не кэшируется «один на всех».
Рейл: без текущего товара (`owned` по SKU), без проданных/забронированных (`IN_STOCK_WHERE`),
`fits: true`. «Усі деталі на {авто}» ведёт на страницу модели (`/brand/<brand>/<model>` —
brand-slug берётся из depth-2 lookup в `favoritesData`, cookie его не хранит).
**Состояния:** авто не выбрано → вкладки нет; авто = модель товара → вкладки нет (это «Ще з
цього авто»); авто выбрано, деталей нет → вкладка с 0 + «Поки немає інших деталей тут».
Вкладки «На ваше авто» **нет в экспорте** DLSRecommend (проектное расширение) — состояния
дефолтные (вопрос ниже).

### Пункт 5 — ревалидация кэша (ADR 006): таблица

Фактическое состояние (из `src/payload.config.ts` + `src/lib/data/revalidate.ts`): хуки

| categories | `categories` | `withRevalidate(Categories)` | getCategoryTree, getCatalog, getMegaMenu, **footer** |
| settings (глобал, `delivery`) | `settings` | `globalRevalidate('settings')` | getSettings |

| partTypes / donors / banners / reviews | `part-types`/`donors`/`banners`/`reviews` | `withRevalidate(…)` | reco / getReviews / banners |

Всё из требования (цена товара, quantity/inReserve, settings.delivery, пункт hotOffers,
