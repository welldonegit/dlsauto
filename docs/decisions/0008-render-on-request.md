# ADR 008 — Рендер фронта по запиту до етапу 9

- **Статус:** прийнято (етап 3c, тимчасове рішення до етапу 9).
- **Контекст:** збірка (`pnpm build`, CI-крок `Build`, Docker-таргети `builder`/`web`) іде **без доступу до БД** — Postgres у CI/Docker немає (Dockerfile: «no DB access needed», DEV_CONTEXT §2). Фронтові сторінки читають дані з Payload/Postgres (home → `getPage`, каталог → `getCatalog`, товар → `getProductBySku` тощо). Якщо будь-яка з них пре-рендериться на етапі збірки, `next build` падає на спробі з'єднатися з БД. Локально збірка була «зеленою» лише тому, що у власника піднятий Postgres і преконект проходив — звідси червоні CI/Deploy з 04.11 (див. грабля в CLAUDE.md, STAGE_3C_REPORT «Починка CI 26.11»).
- **Рішення:** фронтовий лейаут `src/app/(frontend)/[locale]/layout.tsx` — `export const dynamic = 'force-dynamic'`: сторінки рендеряться **по запиту**, не на збірці, тож БД на етапі `next build` не потрібна. Дані кешуються на рівні data-layer через `unstable_cache` з тегами (ADR 006); ревалідація — хуками `withRevalidate` колекцій/глобала. Тобто кеш лишається (швидко), але перший рендер — рантайм, а не білд-тайм.
- **Відкинуто:**
  - **БД на етапі збірки** (підняти Postgres у CI та Docker builder) — тягне сервіс у pipeline і в образ, суперечить «web-образ без БД»; складніше й повільніше, заради того, що на етапі 9 має стати статикою/ISR.
  - **Повний SSG усіх сторінок** зараз — каталог/товар залежать від остатків KeyCRM (змінюються часто), а генерація на білді без БД неможлива.
- **Переглянути на етапі 9 (Продуктивність: ISR, кеш, картинки):** повернутися до часткової статичної генерації / ISR без доступу до БД на збірці — напр. `generateStaticParams` з ревалідацією по тегах, ISR для стабільних сторінок (категорії, марки, проданий товар), рантайм лише для змінних остатків. Мета — прибрати `force-dynamic` там, де сторінка може кешуватися статично, не повертаючи БД у білд. Замір Lighthouse mobile ≥ 90 на реальному залізі.
